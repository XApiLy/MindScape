# MindScape 关键决策记录

> 本文记录已经达成的产品决策及其理由。状态包括：`已确认`、`暂定`、`已取代`。

## D-001：MindScape 不定位为单一学习软件

- 日期：2026-08-13
- 状态：已确认
- 决策：MindScape 是模型无关的 AI 工作空间，学习只是众多使用场景之一。
- 原因：项目讨论、软件开发、创作和普通聊天经常交叉出现，单一学习定位会限制产品和 AI 的能力。

## D-002：AI 是引擎，MindScape 是能力与工作操作层

- 日期：2026-08-13
- 状态：已确认
- 决策：不自建一套僵硬的 AI 行为体系，不用固定教学流程约束模型；重点建设上下文、工具、交互和成果层。
- 原因：基础模型会持续升级，产品应从模型能力提升中受益，而不是被固定流程锁死。

## D-003：使用可组合会话协议，不使用互相隔离的硬模式

- 日期：2026-08-13
- 状态：已确认
- 决策：学习、开发、项目和创作等是会话意图预设，可改变、可组合、可覆盖。
- 原因：真实任务具有混合性。预设能降低上手成本，但不应成为功能边界。

## D-004：通过前两轮对话进行意图识别和能力建议

- 日期：2026-08-13
- 状态：暂定
- 决策：系统根据会话前一到两轮识别任务、项目和期望成果，并按需建议或准备 Skill、MCP、插件、项目上下文和工作方法。
- 原因：减少用户手动配置，让能力自然贴合当前工作。
- 约束：识别和装载过程必须透明、可解释、可调整；敏感操作与外部副作用不能因自动识别而绕过授权。

## D-005：规范成果，而不是限制 AI 表达

- 日期：2026-08-13
- 状态：已确认
- 决策：保留 AI 的自由回答，同时识别决策、任务、风险、代码、引用和文档等结构，并将其转化为可操作成果。
- 原因：用户需要的是可继续推进的结果，而不是被模板压缩的模型能力。

## D-006：首次引导通过真实任务完成

- 日期：2026-08-13
- 状态：已确认
- 决策：不采用可被连续跳过的弹窗教程，改为让用户带着真实目标完成第一次会话和成果交付。
- 原因：用户在获得即时价值的过程中更容易理解产品。

## D-007：建立持续本地记录

- 日期：2026-08-13
- 状态：已确认
- 决策：每次产品讨论和实现更新都维护当前共识、关键决策和讨论日志。
- 原因：防止重要判断只存在于聊天记录中，并保留方向变化的依据。

## D-008：第一阶段聚焦 AI 会话工作平台

- 日期：2026-08-13
- 状态：暂定
- 决策：优先实现意图识别、透明能力装载、上下文控制和成果沉淀；HyperPhase 桌面捕捉等能力随后接入。
- 原因：先验证最核心的 AI 协作闭环，避免被截图、视频、社区、插件市场等大范围功能分散。

## D-009：认知型能力由持续任务模型智能编排

- 日期：2026-08-13
- 状态：已确认
- 决策：认知型能力不能依据关键词一次性装载。系统需要理解目标、任务阶段、约束、缺口和期望成果，形成最小能力组合，并根据对话效果持续重规划。
- 原因：同一个“开发”任务可能处于产品讨论、技术研究、架构设计、编码或审查阶段，固定映射无法提供真正相关的能力，还可能污染上下文。
- 约束：选择理由、置信度和能力变化对用户透明；用户可以固定、替换、禁用和纠正。

## D-010：外部 AI 会话是一等上下文来源

- 日期：2026-08-13
- 状态：已确认
- 决策：提供 Claude、Codex 等外部 AI 会话导入入口，将其保真转换为统一会话图，并支持继续、合并、提炼、检索和成果化。
- 原因：用户的重要上下文已经分散在多个 AI 平台。只有接续既有工作，MindScape 才能成为真正的模型无关工作空间。
- 约束：保留原始文件和来源；派生分析不覆盖原文；不把整段长会话无差别塞给模型；导入内容中的命令和工具指令不得自动执行。

## D-011：会话导入优先采用用户主动提供的数据

- 日期：2026-08-13
- 状态：暂定
- 决策：第一阶段支持上传导出文件、导入文件夹和粘贴内容；后续再增加浏览器辅助导入与授权连接器。
- 原因：主动导入的权限边界清晰、格式可测试、隐私风险较低，也能先验证会话理解和迁移的核心价值。

## D-012：分析深度由两个价值指标驱动

- 日期：2026-08-13
- 状态：已确认
- 决策：在深入分析消息、文件或会话前，先判断目标相关度和决策价值。只有相关且深入后可能改变结论、行动、能力装载或风险判断的内容，才自动获得更多分析预算。
- 原因：全量分析会浪费 Token、增加延迟并制造无关结果；只做关键词摘要又不足以识别真正问题。
- 约束：Token、费用、延迟和隐私作为预算限制；指标判断可被用户查看和纠正。

## D-013：复杂能力采用渐进披露

- 日期：2026-08-13
- 状态：已确认
- 决策：默认界面只呈现关键识别、问题和建议动作；高级用户可展开意图模型、证据、能力变化、工具调用和完整分析记录。
- 原因：简单用户和高级用户需要的是不同信息密度，而不是两套互不兼容的产品。

## D-014：漫游分析作为显式可复用配方

- 日期：2026-08-13
- 状态：已确认
- 决策：提供“漫游分析”，允许用户对任意数据或会话按照一套保存的标准进行广域分析，包括目标、观点、决策、风险、工具调用、成果和潜在线索。
- 原因：部分用户需要的不只是解决当前问题，而是系统性理解全部资料并发现尚未提出的问题。
- 约束：漫游分析不默认启动；必须具有明确范围、深度、预算、隐私边界和停止条件，所有结论可回溯原文。

## D-015：智能系统采用确定性外壳与概率语义内核

- 日期：2026-08-13
- 状态：已确认
- 决策：格式、权限、预算、状态版本、审计和回滚由确定性程序控制；模型只负责需要语义理解的概率判断，且输出结构化结果、证据和置信度。
- 原因：无法保证模型永远判断正确，但可以保证错误可见、可纠正、不直接越权，并能够通过回放和评测持续改进。

## D-016：任务状态采用事件溯源和增量更新

- 日期：2026-08-13
- 状态：暂定
- 决策：原始消息、导入、用户修正、能力变化和工具结果保存为不可变事件；当前任务模型由事件增量归并生成，并保留历史版本。
- 原因：需要解释“为什么系统这样理解”，支持纠错、回滚、导入合并和算法升级后的重新计算。

## D-017：先建设评测管线，再扩大 Skill 和 UI 范围

- 日期：2026-08-13
- 状态：已确认
- 决策：第一阶段先完成统一事件、任务状态、能力清单、回放器和标注评测集，再实现大规模 Skill、复杂画布和自动化体验。
- 原因：没有可回放样本和指标，所谓“更智能”只能凭主观感觉判断，无法稳定优化。

## D-018：导入目标与分析档位分离

- 日期：2026-08-13
- 状态：已确认
- 决策：用户导入会话后，可以选择原样继续、快速识别、详细分析或漫游分析；“继续会话”“并入项目”等目标不强制绑定某个分析档位。
- 原因：部分会话短且目标清楚，分析没有必要；复杂会话则可能从结构化理解中明显获益。
- 约束：不分析仍执行本地格式解析、完整性检查和安全隔离，但不调用模型做语义提炼。

## D-019：分析推荐必须证明增量价值

- 日期：2026-08-13
- 状态：已确认
- 决策：系统可以推荐分析，但不得宣称分析永远优于原样继续。推荐必须展示原因、预计收益、范围、成本和数据发送边界；结果必须有原文引用并可撤销。
- 原因：用户信任应建立在可验证收益上，而不是强制默认、复杂度展示或营销承诺。

## D-020：成本展示区分前置分析与后续上下文

- 日期：2026-08-13
- 状态：已确认
- 决策：分析档位同时展示一次性分析成本和后续每轮上下文成本；原样继续不能笼统标记为“最省 Token”。
- 原因：长会话全量续接会反复消耗大量 Token，而只携带最近消息又可能遗漏关键上下文；快速分析可能通过可复用上下文包降低长期成本。

## D-021：默认采用原文与分析双轨接续

- 日期：2026-08-14
- 状态：已确认
- 决策：导入会话时完整保留不可变原文轨；分析仅生成可修正、可删除的接续轨。主 AI 使用精简接续状态，并按需回溯原始消息、附件和工具记录。
- 原因：仅用原文可能成本高且难以跨模型接手，仅用摘要又会损失细节。双轨结构兼顾保真、效率和可纠错性。

## D-022：不承诺复现原平台的相同输出

- 日期：2026-08-14
- 状态：已确认
- 决策：MindScape 以语义连续性、任务连续性和执行状态恢复为迁移目标，不承诺相同提示再次得到逐字相同结果。
- 原因：导出文件通常缺少原平台系统提示、隐藏记忆、精确模型版本、服务端上下文编排和完整工具环境；模型本身也可能具有非确定性。
- 约束：导入后显示接续完整度报告，明确已恢复、部分恢复和无法恢复的状态。

## D-023：MindScape 不定位为 AI IDE

- 日期：2026-08-14
- 状态：已确认
- 决策：MindScape 聚焦学习、探索、知识理解和 AI 会话，不以终端代理、仓库自主修改、持续测试和代码交付为核心能力。
- 原因：模型可以具备编程知识，但产品竞争维度与 Codex 类软件工程代理不同；复制其落地执行面会扩大范围并削弱认知体验。
- 约束：允许解释代码、讨论技术和导入 Codex 会话，但第一阶段不提供 IDE 级执行闭环。

## D-024：透明性以可审计工作轨迹为准

- 日期：2026-08-14
- 状态：已确认
- 决策：展示目标理解、上下文选择、Skill 装载、工具调用、公开判断、证据、假设、反例、结论和验证结果；不承诺或伪造模型不可见的原始隐藏思维链。
- 原因：多数模型 API 不提供完整内部思考，生成一段事后解释也不等于真实内部过程。用户真正需要的是能核验逻辑和来源的透明性。

## D-025：AI 可调用全部已注册认知工具

- 日期：2026-08-14
- 状态：已确认
- 决策：MindScape 内部工具通过统一清单向会话 AI 暴露，模型可以根据目标组合调用搜索、阅读、知识检索、卡片、图谱、计算、可视化和成果生成等能力。
- 原因：工具不应被固定在孤立页面中，AI 应能在对话过程中主动使用软件能力完成更高质量的探索。
- 约束：工具仍遵守权限、预算、隐私和副作用规则；不提供无限制系统控制权。

## D-026：产品进入垂直切片开发阶段

- 日期：2026-08-14
- 状态：已取代
- 决策：停止继续扩展首版理论范围，围绕“导入或粘贴会话 → 选择分析深度 → 继续对话 → 查看透明轨迹 → 调用内部认知工具”建设第一个可运行版本。
- 原因：核心定位和边界已经足够明确，剩余问题更适合通过原型、成本数据和用户体验验证。
- 约束：首版不实现完整无限画布、社区、插件市场、HyperPhase 全套能力、IDE 级执行或多供应商复杂编排。

## D-027：第一版以无限会话画布为核心工作区

- 日期：2026-08-14
- 状态：已确认
- 决策：第一版范围调整为无限会话画布、外部会话导入、多厂商模型 API 与基础 Chat。无限画布不再后置，而是承载会话、分支和接续关系的主要界面。
- 原因：画布是用户能够立即感知的核心差异，也是后续学习、探索和会话迁移能力的共同容器；团队具备前后端并行开发资源，可以承担这一范围。
- 约束：第一版只做二维会话节点、连线、缩放、拖拽、分支和聚焦阅读，不引入 3D、社区、插件市场或 IDE 级执行能力。

## D-028：模型层首版即采用统一多厂商适配器

- 日期：2026-08-14
- 状态：已确认
- 决策：应用层只依赖统一流式事件接口，首批适配 OpenAI-compatible、Anthropic 与 Gemini；DeepSeek、OpenRouter 和自定义服务复用兼容适配器配置。
- 原因：模型无关是 MindScape 的基础定位，首版锁定单一厂商会让会话迁移和模型切换能力从架构上失真。
- 约束：当前原型采用 BYOK；密钥不进入持久化状态。生产版仍需通过桌面安全凭据或后端代理解决密钥安全与浏览器 CORS。

## D-029：第一版采用单一正式范围基线

- 日期：2026-08-14
- 状态：已确认
- 决策：`docs/v1-product-scope.md` 是第一版唯一有效的产品范围基线。第一版由无限会话画布、外部会话导入、多厂商模型 API、基础 Chat 四个核心能力，以及本地保存、安全恢复、首次体验三个支撑能力组成。
- 原因：长期愿景较多，多团队并行时如果没有唯一边界，会分别把 Skill、MCP、生态、HyperPhase、透明推理和云协作提前带入版本，导致核心闭环失焦。
- 约束：新增范围必须说明替换的现有优先级、周期、依赖和验收影响；P1 不得阻塞 P0 发布。

## D-030：总经理职责与工程授权分离

- 日期：2026-08-14
- 状态：已确认
- 决策：本项目对话中的默认职责是产品与经营管理，包括方向、范围、优先级、组织拆分、接口协调、风险和验收。未经用户明确授权，不直接替工程团队实施代码。
- 原因：用户已有前端、后端等工程团队，需要的是统一决策和交付管理，而不是越过组织分工直接开发。
- 约束：可以读取和审查工程产出；任何代码修改、发布或其他工程执行需要明确任务授权。

## D-031：产品内核定义为可追溯会话图运行时

- 日期：2026-08-14
- 状态：已确认
- 决策：MindScape 内核由不可变来源与事件、可持久化会话图、上下文编译器、可替换模型运行时和可验证派生层组成。无限画布是内核的主要视图，Provider 是执行适配器，导入器是外部数据翻译层。
- 原因：如果将画布组件、某个模型 API 或前端消息数组当作产品内核，多团队会把上下文、分支和数据真实性分别实现，导致状态无法恢复、模型无法替换、导入结果无法追溯。
- 约束：原文不可覆盖、关系必须显式、每次运行具有上下文快照、派生不等于事实、UI 不是数据真相、失败必须真实记录。

## D-033：第一版按工作流与交付成果分配任务

- 日期：2026-08-14
- 状态：已确认
- 决策：V1 拆分为 PM、UX、ARC、CORE、DATA、CAN、CHAT、PROV、IMP、AIX、QA、REL 十二条工作流。任务按可独立验收的工程成果分配，不按页面或“前后端共同负责”分配。
- 原因：画布、Chat、导入和 Provider 共同依赖会话图、上下文快照和运行事件。如果按页面分组，各团队容易各自实现上下文和状态，最后无法可靠集成。
- 约束：每项任务只有一个直接负责人；跨团队契约先冻结；现有演示原型不自动计为完成；P0 任务同时满足正式契约、真实数据、失败恢复、测试和安全要求后才能关闭。

## D-032：正式工程独立于旧原型重新建立

- 日期：2026-08-14
- 状态：已确认
- 决策：`desktop/` 为 MindScape 正式桌面工程；`apps/` 下内容仅作为旧原型参考，不作为实际工程或领域契约来源。正式工程采用 Tauri v2、Rust、React、TypeScript、Vite 与 SQLite，并按领域、应用、适配器和 UI 分层。
- 原因：旧原型将会话语义、上下文选择和持久化集中在前端临时状态中，无法满足可追溯、可恢复、可替换模型和多团队稳定协作的内核要求。
- 约束：旧原型不被静默删除；后续能力通过正式工程中的领域契约和 Tauri 命令接入，不直接复制旧前端状态模型。

## D-034：首批五名工程人员承担五条技术主线

- 日期：2026-08-14
- 状态：暂定，待真实姓名与能力确认
- 决策：首批五名工程人员分别承担领域架构与上下文、桌面数据与恢复、无限画布、Chat与工作区、多厂商模型运行时五条技术主线，共负责111个V1任务。导入、接续分析、独立QA、产品设计和发布由后续人员承担。
- 原因：五条主线能够最早形成“输入 → 上下文 → 模型运行 → 持久化 → 画布呈现”的纵向技术骨架，同时保持每个核心模块有唯一责任人。
