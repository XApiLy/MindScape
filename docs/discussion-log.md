# MindScape 讨论与更新日志

## 2026-08-12：从 Explore 分析到自研方向

### 背景

分析了 Explore 的公开产品界面与用户体验报告。Explore 的价值在于将线性对话展开为可分支的知识卡片树，但其核心交互容易被模仿，产品仍缺少难以迁移的生产方式和生态壁垒。

### 初始方向

- 重构 UI 和知识可视化体验。
- 与 Obsidian、Notion、VS Code、GitHub 等工具流转内容。
- 增加网页预览卡片和外部资料辅助。
- 建立可分享、可 Fork 的知识图谱社区。
- 未来开放卡片插件生态。
- 使用高光、来源锚定和 Synthesis AI 将发散对话收敛为成果。
- 将 HyperPhase 的捕捉、截图、视频、溯源和跨 AI 上下文能力整合进 MindScape。

### 核心发现

真正有机会形成壁垒的不是卡片树或视觉风格，而是用户长期积累的内容来源、上下文、关系、决策、筛选习惯和最终成果。

## 2026-08-13：从“聊天学习”修正为通用 AI 工作空间

### 讨论变化

最初尝试将核心收敛为学习闭环，但确认这种定位仍然过窄。MindScape 还需要承载项目构建、开发、创作、分析和普通聊天。

### 达成共识

- 不约束 AI，而是辅助 AI 获得更准确的意图、上下文、工具和交付规范。
- AI 与 MindScape 并行协作，基础模型越强，平台越强。
- 不使用互相隔离的硬模式，改为主要会话意图与可组合设置。
- 会话目标和协作方式应透明呈现为可编辑协议。
- 输出规范的目的是让成果可用，不是让模型只能填模板。
- 新手引导应通过完成真实任务发生，而不是连续点击的产品旅游。

## 2026-08-13：动态挂载 Skill、MCP 与工具

### 新增方向

将 MindScape 进一步理解为 AI 的能力装载与编排平台。系统通过前两轮对话识别用户正在推进的任务，例如 NeoCarry 的开发路线，并据此装载或建议：

- 对应项目上下文
- 学习与资料研究能力
- 产品讨论与路线规划能力
- 开发相关工具
- 决策记录和成果生成能力

### 交互原则

- 识别结果透明。
- 装载的能力透明。
- 读取范围和权限透明。
- 用户能够增加、移除、固定和调整。
- 自动化不能绕过敏感操作授权。
- 低置信度情况下应建议，而不是擅自改变。

### 本轮行动

- 创建 MindScape 本地产品记录结构。
- 整理当前产品共识。
- 建立关键决策日志。
- 约定后续每轮讨论和实现更新同步落盘。

### 下一步待讨论

优先定义“能力装载系统”的最小可行形态：能力的统一数据模型、前两轮识别流程、透明控制界面，以及自动装载的权限边界。

## 2026-08-13：智能认知编排与外部会话迁移

### 认知能力要求升级

确认认知型能力必须由真正理解任务的编排器负责，而不是依赖“开发、学习、创作”等关键词做固定 Skill 映射。系统需要持续维护目标、阶段、约束、缺口和期望成果，并根据实际对话效果增减能力。

认知能力装载遵循以下原则：

- 最小充分，不把所有可能相关的 Skill 都塞入上下文。
- 能识别任务阶段变化并重新规划。
- 能检测能力冲突、重复和低价值装载。
- 给出选择理由和置信度。
- 用户纠正会影响后续选择。
- 自动化过程透明但不持续打扰用户。

### 新增外部 AI 会话入口

MindScape 将支持导入 Claude、Codex 及其他 AI 网站或工具的会话记录。入口包括上传会话文件、导入导出包或文件夹，以及直接粘贴内容。

导入后可以：

- 保留原始会话并按原顺序查看。
- 继续原任务，而不要求用户重新解释全部背景。
- 提取目标、决策、待办、代码变化和未解决问题。
- 合并到已有项目或创建新项目。
- 生成阶段总结、知识结构或可编辑成果。
- 对多个平台中围绕同一项目的会话进行关联与去重。

导入系统保留原文、来源和平台特有信息。AI 分析结果作为派生层存在，不覆盖原始记录。历史会话中的命令和工具指令只作为数据，不会自动执行。

## 2026-08-13：自适应分析预算与漫游分析

### 问题

动态 Skill、MCP、工具和外部会话理解会快速增加产品复杂度。若每份资料都执行全量分析，不仅浪费 Token 和时间，也会让简单用户面对大量不需要的设置与结果。

### 达成共识

- 默认先精准识别问题和需求，不追求把所有内容分析一遍。
- 使用两个核心指标决定是否深入：目标相关度与决策价值。
- Token、延迟、费用和隐私是预算限制，而不是分析本身的价值目标。
- 简单用户默认只看到识别结果、关键问题和建议动作。
- 高级用户可以展开意图、依据、能力选择、工具调用和完整分析细节。
- 使用渐进披露和可调分析偏好统一两类体验。

### 漫游分析

新增“漫游分析”概念：用户可以定义一套分析配方，让任意会话、文件或项目资料都按照相同标准做一次广域扫描。它适合系统理解、资料考古、跨会话关联和发现未被主动提出的问题。

漫游分析显式启用，不作为默认后台行为；用户可设置分析维度、范围、深度、Token 预算、隐私边界和停止条件。

## 2026-08-13：从产品理论转向核心算法

### 核心问题

需要把意图识别、精准分析、能力装载和成果沉淀转换成可编码、可测试、可迭代的系统，而不是继续依赖抽象概念或一个巨大提示词。

### 达成共识

- 不承诺模型判断永远正确，而是保证每次判断有证据、置信度、版本和纠正入口。
- 使用确定性程序管理权限、预算、状态、冲突、审计和回滚。
- 使用模型处理意图、阶段、信息缺口和语义价值等概率判断。
- 原始事件不可变，任务状态通过增量归并形成。
- 相关度和决策价值分解成可观测子信号，不能只让模型凭空输出一个分数。
- Skill 先经过检索得到候选集，再在预算和冲突约束下选择最小充分组合。
- 主模型调用前由上下文编译器组装最小上下文包，调用后由验证器检查成果契约和引用。
- 在复杂 UI 之前建设回放器、标注数据和离线评测。

## 2026-08-13：导入后的分析选择权

进一步明确：导入其他 AI 会话后，“继续做什么”和“分析多深”是两个独立选择。用户可以不做语义分析直接续接，也可以选择快速识别、详细分析或漫游分析。

达成以下原则：

- 不分析仍保留原文并完成本地格式解析和安全隔离。
- 快速识别只提取当前目标、最后进展、关键约束和下一步。
- 详细分析处理完整脉络、决策、分歧、工具调用和成果。
- 漫游分析按照用户保存的配方做广域探索。
- 系统可以推荐档位，但必须说明收益、范围、成本和数据发送边界。
- 不承诺分析永远优于不分析；短会话与明确任务可能更适合原样继续。
- 分析完成后显示发现、引用、压缩收益、未覆盖范围，并允许撤销分析层。
- 成本必须区分一次性分析与后续每轮上下文；长会话原样继续不一定更省 Token。

## 2026-08-14：导入能否保持原会话性能

讨论了“导入前性能为 50、输出为 A，导入后能否完全保持”的问题。结论是：如果只导入可见聊天记录，通常无法完整复现原平台表现，因为系统提示、隐藏记忆、模型版本、采样状态、工具定义、工作区文件和运行环境可能缺失。

明确两种不同目标：

- **保真接续**：尽可能恢复原始消息、附件、工具记录、文件和环境状态，适合同模型或相似环境继续。
- **分析接手**：提炼目标、约束、决策、进度和未解决问题，适合不同 AI、超长会话或状态不完整时继续。

默认采用双轨：完整原文作为证据轨，分析结果作为接续轨。分析不替代原文，用户可以修正或删除分析层。导入后应展示接续完整度报告，说明哪些状态已恢复、部分恢复或无法恢复。

## 2026-08-14：透明推理与非 IDE 产品边界

### 透明性

用户希望 AI 的思考和逻辑过程可见。明确产品不能承诺展示模型不可获得的隐藏思维链，也不能把事后生成的解释冒充真实内部思考。MindScape 应展示可审计工作轨迹：目标理解、上下文选择、能力装载、工具调用、公开判断、证据、假设、反例、结论和验证。

逻辑自洽通过“结论—证据图”表达，每个结论可以回到来源，并显示支持、反驳、依赖和推导关系。模型原生推理摘要与系统重建的可验证依据必须使用不同标签。

### 产品边界

MindScape 不是 AI IDE，也不与 Codex 竞争终端、代码仓库修改、测试和发布能力。即使基础模型具备编程能力，MindScape 的主赛道仍是学习、探索、知识理解和高质量 AI 会话。

### 工具能力

会话 AI 可以发现并调用全部已注册的 MindScape 内部认知工具，包括搜索、网页与文档阅读、知识检索、翻译、卡片与图谱、计算、可视化、测验和成果生成。所有调用展示输入范围、结果、耗时和影响，并服从权限、预算和隐私边界。

新增专项文档：`docs/reasoning-transparency-and-tool-scope.md`。

## 2026-08-21：确认会话数据实体化、本地知识库与混合 RAG 方向

创始人进一步明确：MindScape 不能只保存聊天文本，也不能把“向量数据库 + RAG Prompt”误认为知识内核。会话中的项目、主题、目标、决策、约束、问题、任务、成果、来源、Claim、工具结果和模型运行等内容，需要转化为本地持久化实体，并保留实体之间的关系、证据、状态和版本。用户希望这些数据形成会话知识库，后续可跨会话检索、继续工作和按当前问题选择性注入上下文。

本次确定的实现方向：

1. 原文层保存消息、导入文件、附件和工具结果，永远不可被摘要或实体覆盖。
2. 实体层和关系层保存可复用认知对象及 `supports`、`contradicts`、`depends_on`、`derived_from`、`supersedes` 等显式关系；模型推断先处于 candidate/inferred，用户确认后才能成为项目事实。
3. SQLite 和原文是事实源；全文索引、LanceDB 向量索引和关系缓存都是可重建检索层，不能反向成为唯一数据源。
4. 会话、项目、工作区知识库拥有不同作用域，默认只检索当前会话和当前项目，不能因语义相似自动跨项目泄漏。
5. RAG 采用全文、向量、图关系、来源权威、确认状态和新鲜度的混合检索，检索结果交给 Context Compiler 按 FocusFrame、预算和权限生成冻结上下文；RAG 不得绕过上下文门控。

新增架构提案 `docs/architecture/local-entities-conversation-knowledge-and-rag-20260821.md`，实体层基础待 M2/M3 范围门禁。第一条垂直切片只验证“项目讨论 → 实体确认 → 本地索引 → 新焦点检索 → 带证据回答”，不提前建设复杂知识图谱编辑器或自动永久记忆。

## 2026-08-21：确认 Markdown 知识层、讨论日志和分支记忆隔离

创始人指出，本地会话知识库如果要真正成为个人知识库，Markdown 是最适合用户阅读、编辑和迁移的文本载体，Obsidian 因此可以自然接入。当前项目已经持续维护 `docs/discussion-log.md`，这类讨论日志不只是管理记录，也是长期记忆的重要时间线。创始人进一步提出，主线讨论 MindScape 大方向时，临时修改一行代码、排查一个小问题或验证一个参数，应该放进独立分支，避免琐碎内容污染主线目标和长期记忆。

本次形成两条共识：

1. 采用“Markdown 知识层 + SQLite 运行层 + 向量索引层 + 原始内容层”。Markdown 保存会话记录、项目知识、决策、约束、讨论日志和成果，使用 YAML frontmatter、稳定实体 ID、EvidenceRef 与 Wikilink，并可直接作为 Obsidian Vault 打开。SQLite 继续负责事件、运行状态、事务、版本和可恢复性；LanceDB 只负责可重建 Embedding 索引。
2. 分支是上下文隔离和记忆隔离机制。主线、探索分支、任务分支和复盘分支分别管理继承内容、本地内容、排除内容和可回流成果。任务分支完成后先生成回流候选，只有经确认的决策、事实或成果才能进入主线或项目知识库；会话分支与 Git 代码分支保持概念分离。

新增架构提案 `docs/architecture/markdown-vault-obsidian-branches-and-logs-20260821.md`，当前优先验证“主线讨论 → 创建局部任务分支 → 生成分支日志 → 提炼成果 → 用户确认回流 → Obsidian 可读知识库”的闭环。

## 2026-08-25：确认流式呈现、阅读锁定与会话定位交互原则

创始人指出，流式输出应像被打出来一样有快有慢，但不能因为新文字到达就强制把正在阅读上文的用户拖到页面底部；同时需要“定位到会话”的功能，并在用户主动触发时产生类似磁吸的稳定吸附效果。

核对当前实现后确认，`ChatWorkspace` 的滚动副作用会在每次 `run.content` 或状态变化时直接滚到 `scrollHeight`，这是当前阅读位置被抢夺的直接原因；回答文本也只是直接渲染已收到的正文和闪烁光标，尚无展示队列。由此形成以下边界：原始流式事件、持久化正文、用量和终态必须保持真实；打字效果只能存在于前端展示层，使用可取消的自适应 reveal queue，有快有慢但不能让界面长期落后于真实流；完成、取消、失败或卸载时应 flush，reduced-motion 时直接显示。

阅读区改为显式 `followMode`：只有用户本来就在底部附近才允许跟随；一旦用户上滑、触摸、键盘滚动或拖动滚动条，立即进入阅读锁定，新内容只显示数量提示，不改 `scrollTop`。用户点击“定位到最新”后，当前运行回答以稳定锚点平滑吸附到可读位置，再恢复跟随；结束时不因完成事件强行跳底。画布的“定位当前节点”与阅读区的“定位到最新”分开，流式内容增长不能自动移动画布相机，画布定位只由用户明确触发。

交互与验收规格已写入 `docs/design/streaming-reveal-scroll-and-conversation-locator.md`。本次只锁定产品和工程边界，尚不视为新的员工06派单，也未直接修改生产代码。
