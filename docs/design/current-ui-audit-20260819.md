> 日期：2026-08-19

## 1. 总结

当前正式界面已经具备可用的会话、Chat、画布、阅读、设置、上下文和运行反馈，不需要推倒业务组件。后续重构应保留组件职责与状态流，在外层增加独立背景/氛围运行层，并把散落的表面颜色、边框、模糊和阴影迁移到统一 `Appearance` 解析结果与 `Surface` 原语。

```text
保留：业务状态、命令、焦点语义、键盘与可访问性
修改：页面根层、L2/L3表面、视觉令牌、氛围退让信号
删除：重复硬编码主题值、组件自行决定全局主题的能力
后置：Wallpaper专有运行时、任意用户Shader、声音、3D场景
```

## 3. 必须原样保留的行为

- 当前会话切换、创建及运行中禁止危险切换的规则。
- Canvas/Chat双视图、节点选择、分支类型、继续与重试语义。
- 发送、流式、停止请求、停止失败、运行失败、恢复和部分内容展示。
- Provider可用性、无Key提示、连接测试和安全凭据边界。
- 画布平移、缩放、拖拽、视口落库与重启恢复。
- 对话框的焦点、Esc关闭、`aria-*`、`role=alert/status`和禁用状态。
- 浏览器Preview与真实Tauri运行模式的边界。

任何视觉实现若改变以上行为，均不属于视觉重构，必须退回对应业务负责人审查。

## 4. 需要解耦的现状

1. `styles.css` 与 `conversationCanvas.css` 中存在大量组件级硬编码RGBA、阴影、模糊和边框；它们应逐步映射为语义令牌，而不是机械换色。
2. 画布节点、阅读器、工具条、编辑器、设置对话框各自定义表面，尚无统一的L2/L3/L4层级解析。
3. 当前根背景和局部面板属于同一套深色视觉语言，不能独立组合颜色/壁纸背景与透明/不透明材质。
4. `spin`、流式光标等业务反馈动画与未来氛围动画共享同一CSS环境，但所有权不同；减少动态策略必须分别处理，不能停止必要状态反馈。
5. 当前Canvas由DOM/SVG承担节点与边，未来Pixi只拥有背景、氛围和可证明有收益的图形层，不能接管输入、表单或业务事实。

## 5. 删除与后置清单

### 生产迁移后删除

- 已被语义令牌覆盖的重复颜色、模糊、阴影和边框常量。
- 各业务组件内自行拼装全局材质预设的逻辑。
- 以整屏重遮罩作为复杂壁纸唯一可读性方案的样式。

### 明确后置

- 执行Wallpaper Engine Scene、Application或任意Web脚本。
- 用户输入任意WGSL/GLSL源码或下载第三方Shader包。
- 环境声音、真实天气API与定位权限。
- 没有明确3D产品场景时加载Three.js。
- 把L3每个按钮开放为独立材质编辑器；首批由所在L2区域继承。

## 6. 迁移顺序

1. 先建立纯状态的Appearance类型、默认值、解析器和Classic回退。
2. 增加独立背景/氛围根层，不改业务组件树语义。
3. 抽取L2/L3/L4语义Surface，先迁侧栏与编辑器，再迁节点与阅读器。
4. 接入输入、选择、阅读、对话框、失焦和减少动态信号。
5. 最后删除旧硬编码，并在同一个正式Tauri Build ID上做业务回归。
