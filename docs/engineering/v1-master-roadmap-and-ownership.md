## 1. 这份文档解决什么

本文件只回答三个问题：

1. V1 从现在到发布要经过哪些里程碑。
2. 每个里程碑完成什么、不做什么、如何验收。
3. 员工01～05和后续专项负责人的责任如何贯穿整个 V1。

文档权威关系如下：

```text
docs/v1-product-scope.md
    决定 V1 做什么与不做什么
        ↓
本文件
    决定里程碑顺序、阶段出口和长期责任
        ↓
docs/engineering/<current-milestone-dispatch>.md
    只决定当前里程碑执行窗口的具体派单
        ↓
PEC 当前文件
    只汇报个人最新进展、证据、阻塞和下一步
```

长期任务池不等于同时开工清单。每个人始终最多两个 WIP；只有当前里程碑的任务可以进入开发。

## 2. V1 最终交付

V1 只交付一个完整产品闭环：

> 用户可以直接开始 AI 会话，或导入其他 AI 平台的历史会话，在无限画布中保留上下文和分支，选择不同厂商模型继续，并在关闭与重启后可靠恢复。

V1 包含：

- 基础 Chat。
- 无限会话画布。
- 外部 AI 会话导入。
- 多厂商模型 API。
- 原样、快速、详细三种导入接续方式。
- 本地保存、安全凭据、错误、取消、重试和恢复。
- 不依赖教程的首次使用体验。

V1 不包含：

- Skill / MCP 自动编排与插件市场。
- DeepSeek Harness 产品集成。
- AI IDE、代码仓库修改、终端、测试或部署。
- 云同步、多人协作和社区。
- 漫游分析、完整透明推理图和复杂成果生态。

## 4. M0：工程底座

### 已有结果

- `desktop/` 正式 Tauri、Rust、React、TypeScript、Vite、SQLite 工程。
- 会话、问答节点、语义边、位置和 ContextSnapshot。
- SQLite schema v4、ModelRun 与统一运行事件持久化。
- Mock Provider、Tauri Channel、取消命令、Chat reducer 和画布投影。
- 操作系统安全凭据服务底座。
- Git、CI、评审、PEC 和七文件时效治理。

### 未关闭项

- RC1 尚未正式冻结为 Frozen V1。
- 运行生命周期仍有一部分由前端跨层编排。
- 启动恢复扫描尚未完成。
- 本次 Rust 基线验证被 crates.io / Schannel 环境问题阻断，需要工程环境修复后重新执行。

M0 的未关闭项全部并入 M1，不再单独扩展 M0。

## 5. M1：真实 Chat Alpha

### 目标

证明 MindScape 不是 Mock 演示，而是一款能够安全使用真实模型、可靠保存并恢复的 Chat 应用。

### 范围

- 首个协议底座：OpenAI-compatible。
- 首个真实验收端点：DeepSeek。
- 后端统一运行协调器。
- 真正网络取消、结构化错误、用量与脱敏。
- 运行中强制退出后的明确恢复。
- 画布、阅读视图、节点和视口一致恢复。

### 不做

- 不做导入器。
- 不做 Anthropic、Gemini 同时接入。
- 不做 Harness、Skill / MCP 和视觉重构。

### 出口

在真实 Windows Tauri 应用中完成：配置 Key、发送、流式、停止、重试、错误分类、分支上下文检查、强制退出、重启恢复和 Key 泄漏检查。任一关键项失败，M1 不通过。

M1 具体到人的任务、分支和日期见 [真实 Chat Alpha 派单](v1-execution-dispatch-20260817.md)。

## 6. M2：本地知识与聚焦连续性 Alpha

### 目标

证明 MindScape 能把当前讨论和通用导入会话沉淀为可追溯的本地知识，并让用户通过 FocusFrame 与任务分支保持连续但不污染主线的工作方式。

### 范围

- 通用 Markdown、JSONL 和 TXT 退化会话导入；原文、角色、顺序、时间和未知内容保真保存。
- 文件选择、拖放、粘贴、编码/大小预检、指纹、重复检测、解析版本和完整性报告。
- 导入来源进入会话图，支持原样继续，不强制生成式分析。
- Effective Run Profile：模型、思考模式、预算、参数、上下文和工具权限可见且可回放。
- FocusFrame：继续当前问题、聚焦新问题、从节点分支和原样续接。
- 主线、探索、任务和复盘分支的 `inherit / local / exclude / promote` 记忆作用域。
- Goal、Decision、Constraint、Question、Source、Project、Topic 的有限实体化。
- Markdown 知识投影、讨论日志、EvidenceRef、稳定 ID、frontmatter 和 Wikilink。
- SQLite 事实源、全文索引、至少一个真实本地向量索引和关系邻居检索。
- M1 运行终态、取消、恢复和安全回归，不允许新知识层破坏已有闭环。

### 不做

- 不做 ChatGPT、Claude、Codex 专用导入适配器；这些进入 M3。
- 不做完整快速或详细 AI 分析与漫游分析。
- 不做 Obsidian 插件和完整双向同步；M2 只保证标准 Markdown Vault 可打开、可读、可重新索引。
- 不做复杂知识图谱编辑器、社区知识图谱和自动永久记忆。
- 不执行导入历史中的命令和工具调用。

### 出口

通用导入、Markdown Vault、讨论日志、主线/任务分支记忆隔离、有限实体确认、全文 + 向量 + 关系检索、模型运行控制和 M1 回归在同一个真实 Tauri Release 中通过；删除、否决、过期或分支排除后的内容不会继续作为有效记忆召回。

## 7. M3：跨平台导入与接续分析 Beta

### 目标

在 M2 的实体、日志、分支和检索底座上，证明 MindScape 的模型无关和跨平台接续价值成立。

### 范围

- OpenAI、Anthropic、Gemini、DeepSeek、OpenAI-compatible / OpenRouter。
- 每类 Provider 至少一个真实模型完成流式、停止、错误和用量矩阵。
- ChatGPT、Claude、Codex 专用导入适配器。
- 快速识别：目标、最新进展、关键约束和下一步。
- 详细分析：阶段、决策、分歧、工具记录、成果和未解决问题。
- 分析前展示发送范围、预计成本和隐私边界。
- 原文轨与接续轨分离；分析可修正、删除、重建并引用原消息。
- 从同一冻结上下文切换模型继续，旧节点模型归属不改变。

### 不做

- 不做自动模型路由。
- 不做漫游分析。
- 不做 Harness 运行模式。
- 不做后台全量分析。

### 出口

三种真实平台导出样本能够导入；原样、快速、详细三档结果与费用边界清楚；五类 Provider 真实契约通过；分析失败仍可原样继续。

## 8. M4：V1 发布候选

### 目标

停止新增功能，把 V1 从“能跑”提升到“可交付”。

### 范围

- 全部 P0 E2E。
- 数据库迁移失败、流式崩溃、导入崩溃与备份恢复。
- API Key、日志、导入注入、路径和超大文件安全测试。
- 200 节点性能、冷启动、会话打开和窄窗口验收。
- 会话、节点、导入原文件、分析层和凭据的删除边界。
- Windows 安装包、版本、升级、卸载和回滚。
- 首次使用 3 分钟内完成首次提问或导入。

### 不做

- 不接受任何新 P1 或 V2 功能。
- 不用“已知问题”豁免数据丢失、Key 泄漏、无法停止或无法恢复。

### 出口

全部 P0 通过，P0 阻断缺陷为零；安装包在干净 Windows 环境完成安装、升级和卸载；发布回滚方案经过演练。

## 9. M5：内测与 V1 发布

### 目标

让真实目标用户连续使用产品，验证闭环而非演示脚本。

### 范围

- 选择至少 20 名同时使用两个以上 AI 平台的目标用户。
- 连续 7 天观察首次价值时间、生成失败率、恢复成功率、导入成功率、导入后继续率和分支使用率。
- 每日缺陷分诊，只修 P0 / P1 缺陷，不扩功能。
- 发布说明、已知限制、数据与费用说明。

### 出口

没有数据损坏、安全和核心流程阻断；关键指标可采集且不上传私人会话正文；总经理签署 V1 发布决定。

## 11. 必须追加的四个专项责任席位

员工01～05负责工程主骨架，但不能同时承担独立体验设计、导入、接续分析和发布验收。需要从现有团队明确四名专项负责人：

| 待任命角色 | 开始时间 | 最终负责 | 与核心五人的接口 |
|---|---|---|---|
| 员工06｜视觉与交互设计工程师 | 创始人直接安排 | 视觉语言、交互原型、动效规格、创始人实时确认与真实应用视觉验收 | 不进入统一派单；收到创始人指令后与员工03、04共同落地 |
| 导入负责人 | M3 前 | M3 专用导入适配、完整性报告与平台样本 | M2 通用导入由员工02/04主责，员工01定契约 |
| 接续分析负责人 | M3 前 | `AIX-001～014`，快速/详细分析、引用、版本与质量评测 | 员工01定证据语义、员工02存储、员工05提供统一模型运行 |
| QA / 发布负责人 | M1 即介入，M4 全职 | E2E、恢复、安全、Provider、安装包与发布门禁 | 独立验收所有负责人，不作为其代测人员 |

员工06何时加入具体工作由创始人直接决定，不由阶段派单安排；其视觉工作不得阻塞运行协调器和真实Provider底层开发。M2 的通用导入由员工02/04承担，不以额外导入负责人任命作为开工条件；没有任命接续分析负责人，M3 的快速/详细分析不允许开始；没有独立QA/发布负责人，M4不允许宣布发布候选。

当前 PEC 七文件制度覆盖员工01～06及一份控制文件；员工06固定为视觉与交互设计工程师。导入、接续分析和 QA / 发布负责人确认后，仍需另行决定其报告渠道，不能直接突破七文件硬约束。员工06详细职责见 [视觉与交互设计工程师职责](../design/visual-interaction-design-engineer.md)。

## 12. 任务如何派发

每个里程碑开始时只发布一份阶段派单，规则如下：

1. 每人只有一个主交付和最多一个评审 / 联调任务。
2. 每项交付只有一个直接负责人。
3. 阶段任务必须指向 `docs/v1-work-breakdown.md` 中的稳定编号。
4. 阶段出口未通过，不派发下一阶段开发任务。
5. 发现新需求先进入待评审池，不直接进入个人 WIP。
6. 任何人不能用 PEC 声明代替代码、测试、真实样本或 E2E 证据。
