# PEC 当前窗口与归档制度

> 制度编号：PEC-GOV-001
>
> 状态：V1 生效
>
> 责任人：总经理 / 项目负责人

## 1. 目的

PEC 用于回答“每名员工现在做到哪里、证据是什么、下一步是什么”。当前目录不是历史报告仓库。历史内容过多会稀释时效性，使管理者和协作者无法快速识别最新状态，因此采用“6 文件当前窗口 + 独立不可覆盖归档”的结构。

## 2. 目录结构

```text
Project Engineering Communication/
├── 员工01-主题-YYYYMMDD-HHmm.md
├── 员工02-主题-YYYYMMDD-HHmm.md
├── 员工03-主题-YYYYMMDD-HHmm.md
├── 员工04-主题-YYYYMMDD-HHmm.md
├── 员工05-主题-YYYYMMDD-HHmm.md
└── PEC-提交归档与时效规则.md

Project Engineering Communication Archive/
├── 员工01/
├── 员工02/
├── 员工03/
├── 员工04/
├── 员工05/
└── 控制文件/
```

归档目录按需要创建员工子目录，不要求提前提交空目录。Git 不跟踪空目录。

## 3. 不变量

- 当前目录必须恰好有 6 个文件，全部为 Markdown。
- 员工01～05各有且只有一份当前 PEC。
- 第六份文件是规则入口或当前任务派发，两者不得同时存在。
- 当前目录不得包含子目录、附件、截图、日志或临时文件。
- 员工 PEC 文件名必须符合 `员工NN-主题-YYYYMMDD-HHmm.md`。
- 时间使用 Asia/Shanghai（UTC+8），文件名时间代表正式提交该快照的时间。
- 旧 PEC 必须进入仓库根目录下独立的归档目录，不能留在当前目录，也不能直接删除。

这些条件由 `scripts/check-pec-retention.mjs` 和 CI 的 `repository-hygiene` job 强制检查。

2026-08-15 建立制度时保留的五份员工报告作为迁移基线接受；每名员工下一次替换报告时，必须完整采用本制度第 6 节的内容契约。

## 4. 何时必须提交新 PEC

出现下列任一情况时，员工必须在对应工程 PR 内更新 PEC：

- 完成或实质推进一个已分配任务。
- 修改原方案、领域契约、数据结构、接口或验收标准。
- 得到新的测试、性能、安全或恢复结论。
- 工作进入阻塞、解除阻塞、交接或等待其他员工的状态。
- 计划中的下一步或 WIP 发生实质变化。

纯格式调整、拼写修正和没有状态变化的同步不单独制造 PEC。连续工作可以在一个可验收切片结束时统一提交，但不得在工程 PR 合并后才补写。

## 5. 原子替换流程

员工更新 PEC 时必须执行以下顺序：

1. 从自己的当前 PEC 读取上一状态，编写新的增量快照。
2. 确认归档目标位于 `Project Engineering Communication Archive/员工NN/`，且不存在同名文件。
3. 使用 `git mv` 将旧 PEC 移入归档，不复制、不覆盖、不删除。
4. 在当前目录新增自己的新 PEC。
5. 运行 `node scripts/check-pec-retention.mjs`。
6. 检查 `git diff --summary`，必须同时看到旧文件 rename 和新文件 add。
7. 将归档、新 PEC、对应工程变化放入同一 PR；一般使用同一个提交，无法同提交时也不得让中间提交进入 `main`。

如果新 PEC 尚未完成，应在分支工作区外起草，不能先把第七个文件放进当前目录等待后续清理。

## 6. PEC 内容契约

每份员工 PEC 至少包含以下字段：

```markdown
# 员工NN｜本次主题

> 提交时间：YYYY-MM-DD HH:mm（UTC+8）
> 覆盖任务：CORE-014、DATA-014
> 状态：进行中 / 已完成 / 阻塞 / 等待评审
> 基线提交：<commit SHA 或 PR>

## 相比上一份的变化
## 已阅读与落实
## 本次完成与证据
## 契约、数据和安全影响
## 验证结果
## 风险与阻塞
## 下一步 WIP（最多两项）
## 需要同事配合
```

PEC 必须描述增量变化，不重复粘贴完整任务书。使用“已完成”时必须给出代码、文档、测试、提交或可复现操作作为证据。没有证据的内容只能标记为计划、假设或待验证。

每份新 PEC 的 `已阅读与落实` 必须列出本轮要求阅读的制度、契约或相关员工当前 PEC，并说明至少一项对本人实现、计划或接口判断的具体影响。只有“已阅”或文档摘要不构成有效回执。

## 7. 时效与真实性

- 当前 PEC 是该员工唯一有效的工作状态声明；归档报告只用于追溯。
- 新 PEC 不得回填虚假时间，不以文件系统修改时间判断先后，以文件名和正文提交时间为准。
- 状态变化后应随对应工程提交一起更新，最迟不得晚于该 PR 进入 Ready for Review。
- 超过三个工作日没有新 PEC 不自动代表停工；管理者应结合 Git、任务和阻塞状态核验，不鼓励为了“显得活跃”制造空报告。
- 发现旧 PEC 有错误时，不修改归档文件；在新 PEC 中写明纠正项、原说法、原因和影响。

## 8. 第六文件的使用

默认第六文件是 `PEC-提交归档与时效规则.md`，作为员工操作入口。需要集中派发新一轮任务时，可以用 `任务派发-主题-YYYYMMDD-HHmm.md` 替换它：

1. 将原控制文件移动到 `Project Engineering Communication Archive/控制文件/`。
2. 新任务派发文件必须说明有效期、负责人、任务编号、优先级、依赖和验收条件。
3. 完整制度始终保留在 `docs/engineering/pec-retention-policy.md`，不会因第六文件替换而失效。
4. 新一轮规则或任务派发再次替换时，同样先归档旧控制文件。

## 9. 评审责任

- 员工本人负责真实性、证据和旧报告归档。
- PR 作者负责确保当前目录仍满足 6 文件不变量。
- 对应领域评审者负责确认 PEC 与代码、测试和实际状态一致。
- 项目负责人负责处理例外，不得以口头许可长期绕过 CI。

未通过 PEC 校验的 PR 不得合并。紧急修复也必须在修复 PR 内完成归档和当前 PEC 更新，不能直接污染 `main`。
