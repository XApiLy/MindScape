## 1. 计划结论

本计划把已确认的视觉方向拆成两条严格隔离的执行轨：

```text
设计与独立原型轨（现在可执行）
现状审计 → 可点击原型 → 创始人确认 → 工程规格冻结

生产实现轨（门禁后执行）
视觉状态底座 → 背景与材质 → Wallpaper 适配 → 氛围引擎
→ 工作区集成 → 性能/可访问性 → 统一验收程序
```

当前 M1 派单明确禁止整体视觉重构，V1 范围也只把“主题微调”列为 P1。因此现在可以推进审计、原型和规格，但不能把完整视觉系统静默写入 `desktop/`。生产实现必须同时满足：

1. M1 真实 Chat Alpha 已 Go，或产品负责人书面确认不会干扰其收口。
2. 创始人已在原型中确认视觉方向与首批范围。
3. 项目完成范围变更：明确该系统进入 V1、替换或推迟什么；若不进入 V1，则排到 V1 后。
4. 员工03、04基于同一生产基线完成影响评估，不在两个分支建立平行主题系统。

计划发布不等于生产开工。未通过以上门禁时，只有 `VIS-001～009` 可以进入 WIP。

## 2. 目标与非目标

### 2.1 目标

- 建立背景、组件材质、氛围与区域覆盖彼此独立的视觉架构。
- 同时支持传统不透明界面和毛玻璃/Liquid Glass透明界面。
- 以局部卡片承担可读性，不用整屏重遮罩破坏壁纸。
- 支持颜色、图片、视频和首批兼容 Wallpaper Engine 订阅内容。
- 让云雾、雨和光影带来空间氛围，并在用户工作时自动退让。
- 保持 Chat、画布、Provider、会话图和运行状态完全独立于视觉配置。
- 在真实 Windows Tauri 应用内满足性能、可访问性、恢复和降级要求。

### 2.2 非目标

- 不改变会话图、ContextSnapshot、ModelRun、Provider 或 SQLite 业务语义。
- 不在第一阶段加入声音、真实天气 API、定位权限或在线壁纸商店。
- 不承诺执行 Wallpaper Engine 的 Scene、Application 或任意 Web 脚本壁纸。
- 不用天气或材质表达业务成功、失败、运行中等状态。
- 不在原型阶段替换正式工程，也不以 Review Lab Preview 冒充 Tauri 验收。
- 不因视觉重构提前实现 M2/M3 产品功能。

### 阶段 E：Appearance生产底座

**任务：** `VIS-010～014`  
**理想工作量：** 7～11并行人日  
**允许现在执行：** 否

建议生产结构：

```text
desktop/src/appearance/
├── types.ts             视觉偏好与兼容类型
├── defaults.ts          Classic安全默认值
├── presets.ts           材质与氛围预设
├── resolver.ts          全局设置 + 区域覆盖 + 设备策略
├── runtimeState.ts      焦点、输入、阅读、失焦、减少动态
└── resolver.test.ts     组合、回退与迁移测试

desktop/src/components/appearance/
├── AppearanceRoot.tsx
├── BackgroundLayer.tsx
├── AtmosphereLayer.tsx
└── Surface.tsx
```

状态严格分成三类：

```text
AppearancePreferences   用户持久偏好，不含业务状态
AppearanceRuntimeState  当前焦点、输入、性能与窗口状态
ResolvedAppearance      纯解析结果，组件只消费这一份
```

规则：

- 视觉偏好使用独立、带版本的本地配置，不进入会话图或 ModelRun。
- 默认 `Classic Opaque` 必须在所有资源失败时可用。
- `Surface` 只表达层级和材质，不复制 Chat/画布业务状态。
- CSS变量按语义命名，如表面、文字、边界、遮蔽强度，禁止组件各自硬编码一套主题。
- 未知预设、旧版本配置、丢失资源均回退而不是阻塞启动。

出口：不改业务行为即可切换 Classic、不透明、毛玻璃和 Liquid Glass；所有组合由纯解析器测试覆盖。

#### 生产技术框架约束

创始人已确认桌面与视觉框架：Tauri v2 + Rust；React 19或经评审的SolidJS + Vite；PixiJS v8 + WebGPU主画布；DOM/WebGPU混合界面；Tailwind CSS v4 + Motion One；SQLite + LanceDB使用Rust Native；Three.js仅在明确3D场景下懒加载。

自定义片元着色器是必需能力，不再作为“复杂效果默认避免”。生产实现遵守：

- PixiJS负责背景、氛围和Shader合成，DOM负责输入、按钮、阅读、菜单和焦点语义。
- WebGPU/WGSL为主路径，WebGL/GLSL为兼容回退；渲染器失败时继续回退静态背景与Classic Opaque。
- Shader资源由项目审核、版本化和测试；首批不允许用户执行任意源码或第三方Shader包。
- Shader Uniform只传视觉参数，不传Prompt、消息、Provider、Key或运行终态。
- React/Solid不按帧更新；高频时间与粒子状态留在Pixi ticker/渲染器内。
- Three.js不得因技术栈中存在就进入首包，只有无法由Pixi/WebGPU合理完成的真实3D需求才引入。

### 阶段 F：背景与 Wallpaper Engine 适配

**任务：** `VIS-012～013`  
**理想工作量：** 5～8并行人日  
**允许现在执行：** 否

首批正式支持：纯色、渐变、用户选择的图片和视频；Wallpaper Engine只把能安全识别为静态图片或视频的订阅项目标记为兼容。

技术验证范围：

- 从 Windows Steam 注册信息与 `libraryfolders.vdf` 发现库，不写死单一路径。
- 只读查找 Wallpaper Engine应用及 Workshop `431960` 内容，解析项目元数据和预览。
- Scene、Application和需要执行脚本的 Web壁纸默认标记不兼容/待支持，不启动第三方可执行文件。
- 手动选择路径仍通过 Tauri受控文件入口，校验类型、存在性、大小与可读性。
- 不把用户壁纸复制到 Git、Review Lab归档或验收证据；记录中只保留必要的本地引用和脱敏元数据。
- 文件丢失、Steam库移动、解码失败时立即使用颜色回退，并在设置中给出可操作提示。

出口：兼容状态真实、失败可恢复、不执行不可信内容、应用离线仍可启动和聊天。

### 阶段 H：性能、可访问性、回归与发布

**任务：** `VIS-019～020`  
**理想工作量：** 4～6人日  
**允许现在执行：** 否

必须覆盖以下验收矩阵：

| 维度 | 必测值 |
|---|---|
| 背景 | 纯色、渐变、图片、视频、兼容Wallpaper、资源丢失 |
| 材质 | 不透明、毛玻璃、Liquid Glass |
| 区域 | 侧栏、画布、节点、阅读、编辑器、设置、临时浮层 |
| 业务状态 | 空、加载、流式、停止、完成、失败、恢复、无Key |
| 专注状态 | 空闲、悬停、拖拽、输入、选字、阅读、对话框、失焦 |
| 设备策略 | 默认、低性能、减少动态、高对比 |
| 尺寸 | 1600×1000、1280×720、窄窗、系统缩放125%/150% |

硬门禁：

- 正文普通文本对比度不低于 4.5:1，大文本和关键控件不低于 3:1。
- 减少动态效果下停止连续位移、粒子和非必要转场；功能状态仍清楚。
- 窗口失焦或最小化时暂停高频绘制；恢复时不能突跳或补跑大量帧。
- 默认“轻柔”氛围在10秒采样中无超过50ms的视觉引擎长任务；与关闭氛围相比，CAN-019基准不得出现超过10%的关键交互回退。若基线工具不足，先补测量再宣称通过。
- 200节点画布、真实流式、拖拽、缩放和编辑器输入必须共同验收，不能只测空白演示页。
- 背景资源或视觉配置损坏不能让工作区无法启动。

最终发布必须执行 `scripts/publish-acceptance.ps1 -Label VIS-020`，使用 `artifacts/acceptance/versions/<build-id>/` 中同一个 Build ID。员工03、04和06不得各自编译等价版本；必须验证无开发服务器独立启动并现场看到真实工作区。

出口：自动化检查、性能记录、可访问性矩阵和真实 Tauri视觉验收全部通过，创始人在指定 Build ID上签字。

## 6. 原型评审脚本

每次创始人评审使用同一顺序，避免只被第一眼效果影响：

1. 先用 Classic不透明模式完成一次发送、流式、停止和聚焦阅读，确认业务基线。
2. 切换颜色背景 + Liquid Glass，检查没有壁纸时透明材质仍成立。
3. 切换复杂壁纸 + 不透明组件，检查用户不喜欢透明时仍然清楚。
4. 切换复杂壁纸 + 毛玻璃，分别检查侧栏、阅读区和编辑器的区域覆盖。
5. 依次开启云雾、雨、光影，从关闭到轻柔再到沉浸。
6. 开始输入、选择文字、打开设置和聚焦阅读，确认氛围主动退让。
7. 开启减少动态与低性能模式，确认不是简单把整个界面变黑或失去状态反馈。
8. 在1280×720和窄窗下重复关键操作，检查遮挡、溢出和可达性。

每个评审结论必须引用 Review Lab版本，并说明区域、状态和期望变化。只说“更高级”“再通透一点”不足以直接派发工程任务，由员工06转译为可验证参数与行为。

## 7. 测试与证据策略

### 自动化

- 纯状态测试：预设解析、区域继承、焦点衰减、减少动态、资源失败、配置迁移。
- 组件测试：设置选择、兼容状态、回退提示、背景装载和浮层退让。
- 画布回归：200节点、缩放、拖拽、流式增长和视口恢复。
- Chat回归：发送、停止、失败、恢复、模型设置和输入焦点。
- 视觉截图：固定数据、固定背景许可资产、固定尺寸和固定动画时间点。

### 人工证据

- 原型阶段：Review Lab主线/观察分支、版本说明、截图或短录屏。
- 生产阶段：统一 Build ID、SHA-256、无开发服务器启动、性能记录、减少动态和资源失败演示。
- 证据不得包含 API Key、私人会话、用户订阅壁纸文件或本地敏感路径。

## 8. Git、PR与PEC规则

- 设计原型、生产底座、Wallpaper发现、画布集成、Chat集成和验收必须拆分为独立可回滚 PR。
- 分支使用项目规范的短生命周期分支；不得让一个视觉大分支持续覆盖全部阶段。
- 公共视觉状态类型和持久化版本先合并，再合并消费组件。
- 每个实现负责人同时最多一个主交付和一个评审/联调任务。
- 每次实质推进更新本人唯一当前 PEC，旧 PEC原子归档；当前目录始终保持七份。
- Review Lab观察分支用于创始人中途观察，员工明确确认的版本才进入主线。
- 生产验收只接受正式 Tauri程序，不接受浏览器原型或静态预览替代。

## 9. 回滚与故障边界

- `Classic Opaque` 是永久安全预设，不是临时调试模式。
- 每个新视觉层可以独立禁用；背景失败不连带禁用 Chat，氛围失败不连带禁用材质。
- 偏好配置带版本，迁移失败时备份旧值并回退默认，不改会话数据库。
- Wallpaper资源只读引用，删除主题设置不删除用户的 Steam订阅文件。
- 发生性能或可读性阻断时，优先关闭对应氛围/材质能力并保留新底座，不在业务组件中加入临时旁路。
- 已交付的验收 Build ID不覆盖；修复后生成新 Build ID并保留失败证据。

## 11. 整体完成定义

只有同时满足以下条件，`VISUAL-FOUNDATION-001` 才能标记完成：

1. 创始人确认的原型版本、否决项和后置项均有记录。
2. 背景、材质、氛围与区域覆盖独立组合，Classic模式永久可用。
3. Wallpaper Engine兼容范围真实，不执行不可信壁纸类型，失败可回退。
4. 氛围在工作状态下自动退让，减少动态与低性能策略有效。
5. Chat和画布业务回归、200节点性能、最低尺寸和可访问性门禁通过。
6. 视觉偏好与领域/运行状态隔离，配置损坏不影响会话数据。
7. 同一个正式 Tauri Build ID完成员工03、04、06和创始人验收。
8. 文档、关键决策、测试证据与所有参与者PEC同步完成。
