# MindScape Markdown 知识库、Obsidian 互操作与分支记忆隔离

> 状态：M1 Go 后的架构提案，知识层与分支记忆待 M2/M3 范围门禁
> 日期：2026-08-21
> 目的：把本地会话知识库变成用户可阅读、可编辑、可迁移的 Markdown 知识资产，并用日志和分支隔离保持长期记忆不被临时任务污染。

## 1. 核心判断

Markdown 确实是个人知识库最合适的用户层格式之一，因为它：

- 人可以直接阅读和编辑。
- AI 可以稳定解析和引用。
- 不绑定 MindScape 私有数据库。
- 能被 Obsidian、VS Code、Git 和普通文本工具打开。
- 适合保存讨论、决策、项目背景、资料笔记和成果。

但不能把所有内部数据都强行存成 Markdown。MindScape 需要一个分层模型：

```text
Markdown 知识层：人读、人改、人带走
SQLite 运行层：事件、状态、事务、关系索引、可恢复运行
向量索引层：Embedding 和语义召回
原始内容层：导入文件、附件和不可变来源
```

因此，最稳妥的方案不是“SQLite 或 Markdown 二选一”，而是：

> SQLite 是运行事实和事件的权威来源；Markdown 是用户可见知识的权威投影和可编辑入口；两者通过稳定 ID、版本和事件同步。

## 2. Markdown 知识库的文件模型

建议一个本地工作区可以直接作为 Obsidian Vault 打开：

```text
MindScape Vault/
├── 00-Inbox/                  # 尚未整理的导入和候选记录
├── conversations/             # 会话与分支的可读记录
│   └── <conversation-id>/
│       ├── index.md
│       ├── main.md
│       └── branches/<branch-id>.md
├── projects/                  # 项目知识
│   └── <project-id>/
│       ├── index.md
│       ├── goals/
│       ├── decisions/
│       ├── constraints/
│       ├── questions/
│       └── artifacts/
├── entities/                  # 可复用的人、组织、主题、术语
├── sources/                   # 原始来源的可读引用页
├── logs/                      # 讨论日志、运行日志和阶段复盘
│   ├── discussions/
│   ├── branches/
│   └── daily/
├── indexes/                   # 可重建的目录页和导航
└── attachments/               # 文件引用或内容寻址附件
```

这不是要求用户看到一堆技术文件。MindScape UI 可以把它呈现为项目、会话、知识卡片和日志；文件结构主要服务于持久化、迁移、Obsidian 和高级用户。

## 3. 文件内容与元数据

每个实体或日志文档使用 YAML frontmatter 保存稳定元数据，正文保持普通 Markdown：

```md
---
id: decision-20260821-focus-frame
type: decision
scope: project/mindscape
status: confirmed
branch: main
sourceRefs:
  - msg://conversation-123/node-48
  - run://model-run-902
createdAt: 2026-08-21T14:20:00+08:00
updatedAt: 2026-08-21T14:30:00+08:00
---

# 使用 FocusFrame 隔离当前问题

长会话不默认携带全部历史。新问题只继承已确认的项目约束和用户选择的证据。

相关项目：[[MindScape]]
相关主题：[[上下文编译]]、[[会话连续性]]
来源：[[conversation-123]]
```

要求：

- `id` 永久稳定，文件改名不能改变实体身份。
- `type`、`scope`、`status` 和 `branch` 决定检索与记忆权限。
- `sourceRefs` 必须能回到原始消息、文件或工具结果。
- `[[wikilink]]` 只表达可读关系，权威关系仍保存在领域关系表和事件中。
- 用户编辑 Markdown 后，系统生成新修订和事件，不直接覆盖历史版本。

## 4. 讨论日志是长期记忆的时间线

用户和 MindScape 的每次重要讨论都应该形成日志，但日志要分层，不能只维护一个不断膨胀的文件：

### 4.1 原始讨论记录

保存完整消息、时间、分支、模型和来源。这一层用于保真和回放，不追求适合快速阅读。

### 4.2 可读讨论日志

每次讨论或每个重要阶段生成一条 Markdown 日志，至少包含：

```text
日期与参与者
所属项目与分支
本次讨论目标
形成的共识
新增或修改的决策
未解决问题
引用的来源
下一步
```

当前项目的 `docs/discussion-log.md` 就是这种管理级时间线。未来可同时在 Vault 的 `logs/discussions/` 中生成分支级和项目级版本。

### 4.3 结构化记忆

日志中确认的目标、决策、约束和问题，进一步实体化为独立 Markdown 文件和 SQLite 实体。日志是时间线，实体是可复用对象；不能用一份摘要替代两者。

### 4.4 成本控制

原始事件必须每轮保存，但可读日志和深度实体抽取不必每个普通闲聊都调用昂贵模型。建议：

- 本地追加轻量事件和原文。
- 识别到决策、约束、阶段变化或用户要求时生成可读日志。
- 会话结束或用户点击“沉淀知识”时做一次结构化整理。
- 普通闲聊只索引，不自动晋升为永久记忆。

## 5. 分支是记忆隔离机制

分支不只是画布上的视觉分叉，而是一个独立的上下文工作区。它解决的正是用户提出的问题：主线讨论 MindScape 大方向时，临时修改代码第一行不应该污染产品目标、长期决策和战略记忆。

### 5.1 主线与任务分支

- **主线分支**：产品方向、长期目标、已确认约束和核心决策。
- **探索分支**：研究某个方向，结果不自动成为结论。
- **任务分支**：完成一个局部问题，例如修改代码、排查一个错误或验证一个模型参数。
- **复盘分支**：总结已完成工作，产生可提炼的决策、日志或成果。

任务分支可以继承主线的少量硬约束，例如“MindScape 不做 AI IDE”，但默认不继承主线的全部讨论细节。

### 5.2 分支记忆权限

每个分支都有四个明确集合：

```text
inherit：允许继承的项目事实、硬约束和指定来源
local：只在本分支有效的临时假设、问题和草稿
exclude：明确不带入本分支的主线内容
promote：完成后允许提炼回主线的候选成果
```

例如“修改代码第一行”的任务分支：

```text
继承：项目名称、代码文件位置、相关错误信息
本地：本次修改方案、试验结果、临时假设
排除：MindScape 长期产品讨论、视觉方向争论
回流候选：最终修复说明、影响范围、需要更新的决策
```

### 5.3 分支结果不自动污染主线

任务分支完成后，系统生成“回流候选”而不是直接合并：

```text
任务分支成果
→ 生成修复摘要 / 事实 / 决策候选
→ 标注来源和影响范围
→ 用户确认是否回流主线或项目知识库
→ 创建新版本实体和关系
```

临时讨论、错误尝试和未验证推断可以永久留在分支日志中，但不应被主线 RAG 当成已确认事实。

## 6. Obsidian 连接方式

### 第一阶段：直接打开 Vault

MindScape 直接生成一个标准 Markdown 文件夹，用户可以用 Obsidian 打开。首阶段只承诺：

- MindScape 导出的 Markdown 能在 Obsidian 正常浏览。
- `[[wikilink]]`、标题、标签和 frontmatter 保持可读。
- MindScape 的实体 ID 与 Obsidian 文件名变化解耦。
- 用户在 Obsidian 中添加的笔记可以被 MindScape 重新索引。

### 第二阶段：增量同步

后续再增加文件变更监听和双向同步：

- Obsidian 修改生成一个新修订事件。
- MindScape 重新解析 frontmatter、正文和链接。
- 冲突保留两份版本，不能静默覆盖。
- 只把符合格式和作用域的 Markdown 提升为实体或关系。

不建议一开始承诺“完整 Obsidian 双向同步”。先保证文件可读、实体可回溯、修改可发现，再处理冲突和复杂插件语法。

### 第三阶段：知识视图互通

成熟后可以提供：

- 在 MindScape 中打开实体对应的 Obsidian 文件。
- 在 Obsidian 中通过链接回到 MindScape 会话和来源。
- 用 Dataview 风格字段生成项目决策、未解决问题和分支索引。
- 将会话分支、讨论日志和成果按模板生成笔记。

## 7. RAG 如何读取 Markdown 与分支

Markdown 进入检索前按标题、段落、列表和代码块切分，每个 Chunk 必须带：

- 文件 ID 和路径。
- 实体 ID、关系 ID 和来源引用。
- 项目、会话和分支作用域。
- `confirmed / inferred / rejected / stale` 状态。
- 创建和更新时间。
- 原文哈希和分块版本。

检索流程为：

```text
当前问题 + 当前分支
→ 过滤作用域与排除集合
→ FTS 精确召回
→ 向量语义召回
→ Wikilink / 关系邻居扩展
→ 状态、来源和新鲜度重排
→ Context Compiler 按预算裁剪
→ 生成带路径和引用的上下文包
```

因此，Markdown 可以成为 RAG 的重要知识来源，但模型拿到的是经过分支隔离、证据筛选和预算控制的内容，不是整个 Vault。

## 8. 与 Git 分支的区别

MindScape 的会话分支、知识分支和 Git 代码分支不能混为一谈：

- 会话分支隔离讨论目标和模型上下文。
- 知识分支隔离实体、日志和待确认记忆。
- Git 分支隔离代码变更和工程提交。

它们可以通过来源链接关联，但不能因为用户在 MindScape 里创建了任务分支，就自动修改 Git 分支、提交代码或执行本地命令。MindScape 仍然不是 AI IDE。

## 9. 第一条验证闭环

```text
主线：讨论 MindScape 长期方向
→ 创建任务分支：修改一个局部代码问题
→ 任务分支只继承项目边界和相关文件信息
→ 记录本分支的过程日志与结果
→ 生成回流候选
→ 用户选择：只归档 / 写入项目知识 / 更新主线决策
→ 主线继续时只看到确认后的成果
```

验收标准：

1. 任务分支中的临时错误不会被主线检索为事实。
2. 主线的已确认约束可以被任务分支继承。
3. 分支日志能回到每个原始消息和工具结果。
4. 用户可以把分支成果提炼为 Markdown 实体和项目决策。
5. Obsidian 打开 Vault 后可以读懂项目、会话、日志和实体之间的链接。
6. 删除或否决分支成果后，RAG 不会继续召回旧的有效记忆。

## 10. 当前边界

这项方案不等于立即建设完整知识图谱编辑器、Obsidian 插件市场或 Git 自动化。第一阶段只做：

- Markdown 知识投影。
- 讨论日志和分支日志。
- 稳定实体 ID、frontmatter 和 EvidenceRef。
- 主线 / 任务分支的记忆隔离。
- 从 Markdown 和 SQLite 共同建立混合检索索引。
- 分支成果的显式回流。
