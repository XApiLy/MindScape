# MindScape 本地实体、会话知识库与混合 RAG 方案

> 状态：M1 Go 后的架构提案，实体层基础待 M2/M3 范围门禁
> 日期：2026-08-21
> 目的：把会话、导入资料和工具结果转化为本地可追溯的认知实体，支持跨会话知识库、混合检索和按焦点编译上下文。

## 1. 先统一一个认识

MindScape 不应该只是：

```text
聊天记录 + 向量数据库 + 一个 RAG Prompt
```

真正需要建设的是：

```text
原始来源
  → 结构化实体与关系
  → 可验证的派生知识
  → 关键词 / 向量 / 图关系混合检索
  → 有预算的上下文包
  → 模型运行与成果回写
```

RAG 是检索和供给上下文的执行机制，不是 MindScape 的数据模型。向量相似度也不能代替事实、关系、来源和用户确认状态。

## 2. 四层数据模型

### 2.1 原文层 Raw Source

保存用户真正提供或系统真正产生的内容：

- 用户消息和 AI 消息。
- Claude、Codex 等外部会话原文。
- 文档、图片、音频和附件。
- 工具调用和工具返回。
- Provider 返回的公开正文、用量和运行状态。

原文层不可被摘要、向量或实体抽取覆盖。原文保存内容指纹、来源平台、位置、时间、修订和解析版本。

### 2.2 实体层 Entity

把原文中可被后续工作引用的对象变成结构化实体。第一批不追求“识别世界上的一切”，只处理对会话和项目有价值的认知对象：

| 实体 | 示例 |
| --- | --- |
| Conversation | NeoCarry 产品路线讨论 |
| Person / Organization | 创始人、DeepSeek、某个团队 |
| Project | MindScape、NeoCarry |
| Topic | 上下文压缩、模型思考控制 |
| Goal | 让长会话保持聚焦和连续 |
| Decision | M1 已 Go；使用 FocusFrame |
| Constraint | 不做 AI IDE，不执行本地代码 |
| Question / Gap | 是否默认启用项目记忆 |
| Task | 建立模型能力目录 |
| Artifact | 架构文档、验收报告、代码片段 |
| Claim | 一个带证据和状态的事实或判断 |
| Source | 消息、文件、工具结果或外部链接 |
| ModelRun / ToolRun | 一次模型运行或工具调用 |

实体必须有稳定 ID、类型、名称、别名、作用域、状态、版本和来源引用。它不是从原文复制出来的一段摘要，而是一个可被其他会话引用的领域对象。

### 2.3 关系层 Relation

实体之间的关系必须显式保存，不能只依赖向量相似度：

- `mentions`：消息提及实体。
- `belongs_to`：实体属于项目或会话。
- `supports`：来源支持某个 Claim 或 Decision。
- `contradicts`：两个 Claim 或 Decision 相互矛盾。
- `depends_on`：任务或决策依赖某个约束。
- `derived_from`：派生实体来自原文或其他实体。
- `supersedes`：新决策取代旧决策。
- `related_to`：弱关系，仅作为检索线索。
- `continued_by`：一个会话分支继续另一个工作项。

关系也必须记录来源、生成器、置信状态和有效时间。关系不是视觉连线的附属物，画布只显示领域关系的投影。

### 2.4 检索层 Index

检索层可以有多个索引，但都不能成为事实源：

- SQLite 结构化查询和事务是权威事实源。
- SQLite FTS5 或等价全文索引处理精确词、名称、代码和中文关键词。
- LanceDB 或其他向量索引处理语义召回。
- 关系邻接索引处理项目、决策、证据和分支的图遍历。
- 时间、作用域、来源权威性和用户确认状态用于过滤与排序。

向量索引损坏、模型更换或重新嵌入时，可以从 SQLite 和原文层重建；不能反过来从向量库恢复全部领域事实。

## 3. 会话知识库不是单一“大脑”

MindScape 至少要区分三个作用域：

1. **会话知识库**：当前会话中形成的目标、事实、决策、问题和引用。
2. **项目知识库**：跨会话共享、用户确认过的项目实体和关系。
3. **工作区知识库**：用户明确允许跨项目检索的通用资料、术语和偏好。

默认检索范围只能是当前会话和当前项目。跨项目、私人资料、导入会话和云端内容必须有明确范围，不因“语义相似”自动泄漏。

实体的生命周期建议固定为：

```text
candidate → inferred → confirmed
                    ↘ rejected / superseded / stale
```

模型可以抽取候选实体和候选关系，但不能无确认地把推断提升为项目事实。用户确认、否决或修订应通过新事件完成，保留旧版本和证据。

## 4. 实体化流程

实体化不应在每次消息后都调用昂贵模型做全量总结。建议采用分层流水线：

```text
消息 / 文件 / 工具结果进入事件账本
→ 本地结构解析、分块、指纹、名称和时间抽取
→ 只对高价值片段做候选实体与关系抽取
→ 实体规范化、去重和冲突检测
→ 写入 candidate / inferred 派生层
→ 用户确认或系统根据低风险规则晋升
→ 更新全文索引、向量索引和关系索引
```

实体抽取的触发方式可以是：

- 用户点击“沉淀为知识”。
- 系统识别到新决策、关键约束或高价值成果。
- 会话结束时的轻量整理。
- 用户对项目知识库执行“整理”或“漫游分析”。

普通闲聊不应该自动产生大量永久实体。系统可以保存原文并建立低成本索引，等到用户真正检索或确认时再深入抽取。

## 5. 混合 RAG，不是单一向量搜索

每次检索建议经过以下流程：

```text
当前输入 + FocusFrame
→ 生成结构化检索条件
→ 关键词 / 精确实体召回
→ 向量语义召回
→ 从命中实体扩展证据和关系邻居
→ 按相关度、决策价值、来源权威、确认状态和新鲜度重排
→ 去重、冲突标记和 Token 预算裁剪
→ 生成带 EvidenceRef 的上下文包
```

### 为什么必须混合

- 纯向量容易把“相似但不相关”的内容召回。
- 纯关键词抓不住用户换一种说法表达的同一问题。
- 纯图遍历会过度扩散，带入一堆关系但缺少语义重点。
- 只检索摘要会丢失原文细节和反例。

因此至少使用三种信号：

```text
retrieval_score
= semantic_score
  + lexical_score
  + graph_proximity
  + authority_bonus
  + confirmation_bonus
  + recency_adjustment
  - conflict_penalty
  - scope_penalty
```

首版不需要承诺一个完美数学公式，但每个命中结果必须能解释“为什么被选中”。

## 6. 与上下文编译器的关系

实体知识库不直接把全部结果发送给模型。它只向上下文编译器提供候选证据：

```text
FocusFrame
  + 当前问题
  + 已确认约束
  + 当前分支实体
  + 检索命中的 Claim / Decision / Source
  + 用户指定资料
        ↓
Context Compiler
        ↓
有限、冻结、可审计的 ContextSnapshot
```

上下文快照至少要记录：

- 使用了哪些实体、关系和原文片段。
- 每项内容来自哪个作用域。
- 哪些命中被排除及原因。
- 实体和索引版本。
- 估算 Token 和实际 Provider 用量。
- 冲突、低置信度和未验证假设。

这样模型得到的是“与当前问题有关的知识包”，而不是不可控的知识库转储。

## 7. 本地数据实现建议

### 权威存储

- SQLite：Workspace、Conversation、Message、Source、Entity、Relation、Claim、EvidenceRef、ModelRun、事件和版本。
- 本地内容寻址目录：原始导入文件、附件和较大内容块。
- 操作系统安全凭据：Provider API Key；数据库只保存凭据引用。

### 索引存储

- SQLite FTS5：名称、标题、中文全文和精确检索。
- LanceDB：向量 Embedding、模型版本、维度、来源 ID 和索引状态。
- 可选关系缓存：从 SQLite 关系表重建，不作为独立事实源。

### Embedding 管理

每个向量必须记录：

- embedding 模型和版本。
- 维度和归一化方式。
- 源内容哈希。
- 分块策略版本。
- 创建时间和索引状态。

更换 embedding 模型时建立新索引并后台重建，不能覆盖旧索引后让历史 ContextSnapshot 失去可重放能力。

本地 Embedding 优先用于隐私和成本控制；允许用户选择云端 Embedding 时，必须在发送前显示数据范围、Provider、费用和保存策略。

## 8. 数据安全与删除

- 原文、实体、关系和向量索引必须绑定作用域。
- 用户删除一个来源时，原文、派生实体、关系和向量都要进入同一删除事务或可审计删除队列。
- 向量索引中的孤儿记录不能继续参与检索。
- 用户否决的实体不能通过旧向量重新召回为已确认事实。
- 导入会话里的提示、命令和工具调用始终是数据，不自动执行。
- 日志和检索诊断不得包含 API Key、私人原文或未脱敏的工具响应。

## 9. 第一条可开发垂直切片

先不要建设完整知识图谱 UI，做一条最小但真实的闭环：

```text
用户发送 5～10 轮项目讨论
→ 本地保存原文
→ 抽取 Goal / Decision / Constraint / Question / Source
→ 用户确认其中 2～3 条
→ 写入 SQLite 实体与关系
→ 建立全文和向量索引
→ 用户在新 FocusFrame 提问
→ 混合召回相关实体与原文证据
→ ContextSnapshot 显示引用和排除项
→ 模型回答并可回溯来源
```

垂直切片的成功标准不是“向量命中了多少”，而是：

1. 新问题可以准确找到已确认的项目事实。
2. 无关会话不会污染当前答案。
3. 每个关键结论都能回到原始消息或文件。
4. 用户否决或修改实体后，后续检索会立即遵守新状态。
5. 删除来源后，派生实体和向量不会继续泄漏该内容。

## 10. 与现有 V1 边界的关系

实体化是内核能力，不等于第一版要做一个知识图谱产品。第一版的主对象仍是 Conversation；实体、关系和向量索引先服务于：

- 会话连续性。
- 跨会话检索。
- 导入会话接续。
- 上下文压缩和 Token 控制。
- 透明引用和成果沉淀。

暂不做：

- 面向用户的复杂图谱编辑器。
- 社区共享知识图谱。
- 自动把所有聊天变成永久记忆。
- 只依赖向量相似度的“万能记忆”。

## 11. 必须冻结的内核原则

1. SQLite 和原文是事实源，向量只是索引。
2. 实体化是派生过程，不能覆盖原文。
3. 关系和来源与实体同等重要。
4. 用户确认状态高于模型推断。
5. 会话、项目和工作区必须有清晰检索作用域。
6. Context Compiler 决定最终发送范围，RAG 不能绕过预算和权限。
7. 索引可重建，历史快照必须可回放。
8. 删除、否决、过期和冲突必须影响后续检索。
