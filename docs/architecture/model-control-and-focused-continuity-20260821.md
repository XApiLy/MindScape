# MindScape 模型控制与聚焦连续性方案

> 状态：M1 Go 后的架构提案，待 M2 范围门禁批准
> 日期：2026-08-21
> 目的：让用户显式控制模型、思考强度、生成参数和上下文范围，同时保留连续工作的记忆价值，避免把整段历史对话反复塞回模型。

## 1. 核心结论

MindScape 不把“连续会话”实现为每一轮都携带全部历史，也不把“新建会话”作为唯一的聚焦手段。每轮运行都从同一份不可变事件和结构化记忆中，编译出一个新的、可审计的上下文包：

```text
原始事件与完整历史
        ↓
当前聚焦问题 / 当前工作项
        ↓
已确认记忆与约束
        ↓
按相关度、决策价值和预算检索证据
        ↓
本轮上下文包 + 模型控制档案
        ↓
一次独立、可回放的模型运行
```

因此，一轮运行既可以像“新会话”一样只关注眼前问题，也可以继承项目中已经确认的事实、决策和约束。连续性来自结构化记忆和可选证据，不来自无界增长的聊天剧本。

M1 已经 Go。本方案是 M1 之后的增量设计，不改变当前 `mindscape.context.v1`、`mindscape.runtime.v1` 的冻结语义；新增能力应通过加法字段、版本化快照和新的运行控制档案接入。

## 2. 产品边界

### 要解决的问题

1. 用户能选择哪个 Provider 和哪个模型执行下一轮。
2. 用户能控制思考模式和预算，而不是被厂商默认值静默决定。
3. 用户能调整温度、输出长度、工具策略和上下文范围。
4. 长会话不会因为历史累积而无限增加成本、延迟和偏题风险。
5. 新问题可以保持聚焦，同时按需继承项目记忆。
6. 每次运行都能说明实际使用了什么、跳过了什么、为什么这样选。

### 不做的事

- 不承诺展示模型不可观测的完整隐藏思维链。
- 不把模型生成的事后解释伪装成真实内部思考。
- 不自动把所有历史消息永久提升为记忆。
- 不让“思考更深”绕过权限、预算或外部工具确认。
- 不把 MindScape 变成 IDE、终端 Agent 或本地执行代理。

## 3. 模型控制面板

每次发送前都存在一份“有效运行档案（Effective Run Profile）”。它记录本轮最终使用的配置，以及每个值的来源：用户明确设置、会话继承、项目继承、系统建议或 Provider 能力限制。UI 可以提供简洁预设，但不能隐藏有效值，也不能静默改写用户选择。

### 3.1 用户可见的五个控制组

| 控制组 | 首要控制 | 高级控制 |
| --- | --- | --- |
| 模型 | Provider、模型 | 上下文窗口、输入模态、工具能力、价格和延迟 |
| 思考 | 关闭、标准、深入、自定义 | 思考预算、厂商 reasoning effort / thinking budget 映射 |
| 上下文 | 当前问题、当前分支、项目记忆、指定历史 | 片段选择、排除项、输入预算、记忆版本 |
| 工具 | 不调用、自动调用、每次询问 | 允许的 Skill/MCP、调用次数、网络和写入权限 |
| 输出 | 简洁、标准、长文 | temperature、top_p、max output tokens、结构化格式、seed（能力允许时） |

普通用户只需要看到五个选择器；高级用户展开后可以编辑实际参数。发送按钮附近要显示一条可读摘要，例如：

```text
DeepSeek V4 Flash · 深入思考 4k · 当前问题 + 项目记忆 · 工具自动调用 · 输出上限 2k
```

### 3.2 思考模式的统一语义

MindScape 定义跨厂商的抽象层，但不假装各厂商的思考能力完全等价：

| 抽象模式 | 含义 |
| --- | --- |
| 关闭 | 尽可能使用直接回答；如果模型不支持关闭，必须明确标注“不支持”，不能静默换模式 |
| 标准 | 使用模型正常的推理预算，适合一般解释和比较 |
| 深入 | 为复杂分析、冲突检查和多步规划提供更高预算 |
| 自定义 | 用户直接指定思考预算或厂商对应参数 |

Provider 适配器负责把抽象模式映射为厂商参数，例如 `reasoning_effort`、`thinking_budget` 或 `max_reasoning_tokens`。无法映射时返回能力不兼容，而不是偷偷删除参数、切换模型或重新发送。

思考预算必须与可见输出预算分开核算。模型可能把输出上限消耗在 `reasoning_content`，导致正文为空；适配器必须把思考事件和正文事件分开，正文为空时不能标记为成功完成。截图所示的 DeepSeek 默认思考问题正是这一契约需要覆盖的案例。

### 3.3 参数的默认与继承

“不能默认”应理解为不能有不可见的默认，而不是要求用户每次手填全部数字。产品允许使用可解释的推荐档案，但每一轮都要展开为实际值并可修改：

```text
来源：系统建议（用户未覆盖）
temperature：0.2
max_output_tokens：2048
reasoning：standard / 1024 tokens
```

用户覆盖后的值只影响下一次或当前作用域，旧节点的运行档案不可被回写。Provider 不支持的参数显示为“此模型不支持”，不做静默降级。

## 4. Provider 能力契约

模型目录不只保存名称，还必须声明能力和限制：

```ts
type ModelCapabilities = {
  contextWindowTokens: number | null
  supportsStreaming: boolean
  supportsReasoning: boolean
  reasoningControl: 'none' | 'effort' | 'token_budget' | 'vendor_specific'
  supportsTemperature: boolean
  supportsTopP: boolean
  supportsTools: boolean
  supportsStructuredOutput: boolean
  inputModalities: Array<'text' | 'image' | 'file' | 'audio'>
  pricing: { input?: number; output?: number; reasoning?: number }
  latencyClass: 'fast' | 'standard' | 'slow'
}
```

发送前由确定性代码完成能力校验：

1. 模型是否能满足本轮输入模态、工具和结构化输出要求。
2. 思考和输出预算是否能放进可信上下文窗口。
3. 用户设置的参数是否被该模型支持。
4. 预计费用、隐私边界和网络范围是否满足运行档案。

校验失败发生在创建 Node、ContextSnapshot 和 ModelRun 之前，不产生残留运行，也不静默切换到 Mock 或其他模型。

## 5. “连续但聚焦”的上下文模型

### 5.1 五层记忆

每轮上下文不直接读取整个会话，而是从五层内容中编译：

1. **当前输入**：本轮问题、用户明确格式和即时约束，永远最高优先级。
2. **短期工作记忆**：当前聚焦问题下最近的少量消息、正在讨论的假设和未完成动作。
3. **活动分支记忆**：当前节点到分支根的已确认目标、决策、约束和关键成果。
4. **项目长期记忆**：用户确认过的事实、项目决策、术语、偏好和可复用成果，全部带来源、状态和版本。
5. **历史档案**：完整原文、旧分支和导入资料，只建立索引，默认不注入；需要时按证据检索。

摘要不能覆盖原文。所有被提升到工作记忆或长期记忆的内容都必须保留 `EvidenceRef`、来源哈希、生成器版本和状态（明确、推断、已确认、被否决、已过时）。

### 5.2 聚焦框（Focus Frame）

“新问题”不一定创建新会话，而是创建一个新的 `FocusFrame`：

```ts
type FocusFrame = {
  id: string
  conversationId: string
  parentNodeId?: string
  objective: string
  activeWorkItem?: string
  include: Array<'recent' | 'branch' | 'project_memory' | 'retrieved_history'>
  excludeRefs: string[]
  memoryVersion: number
  createdAt: string
}
```

用户可以在界面上选择：

- **继续当前问题**：保留当前短期工作记忆。
- **聚焦新问题**：清空短期消息，但保留用户选中的项目记忆。
- **从此处分支**：从某个节点复制目标和必要约束，建立独立焦点。
- **原样续接**：特殊情况下，按原始轨携带指定历史，适合导入会话保真续接。

这使“新开会话的注意力”变成一个可控制的上下文策略，而不是牺牲连续性。

### 5.3 上下文编译顺序

```text
当前输入与硬约束
→ 当前 FocusFrame
→ 已确认的活动分支事实
→ 少量项目长期记忆
→ 与本轮目标高相关且高决策价值的历史证据
→ 用户明确勾选的其他资料
```

上下文编译器必须输出：已选内容、排除内容、排除原因、估算 Token、实际运行档案和快照版本。旧历史不是被删除，而是明确标为“本轮未引用”。

### 5.4 记忆晋升与失效

模型可以提出“建议记忆”，但不能无确认地把推断写成项目事实。用户可将其：

- 固定为项目事实或决策；
- 仅保留在当前焦点；
- 标记错误并让系统重算；
- 设置过期时间或适用范围。

新事实与旧记忆冲突时，保留两者和证据，标记冲突，不能静默覆盖。这样可以避免长对话中早期错误一直污染后续回答。

## 6. 单轮运行流程

```text
用户选择/确认运行档案
→ 能力校验与预算预览
→ 更新当前 FocusFrame
→ 检索候选记忆和证据
→ 相关度 R / 决策价值 D 门控
→ 编译并冻结 ContextSnapshot
→ 以选定模型和参数创建 ModelRun
→ 流式接收正文、思考摘要、工具事件和用量
→ 结果验证：约束、证据、冲突、结构
→ 保存可见成果、建议记忆和本轮账单
```

本地结构解析、索引、去重、预算和权限优先由确定性程序完成；小模型只做低成本候选判断；主模型负责真正的任务回答；验证步骤按风险和用户档案决定是否启用。不要每轮对完整历史进行一次昂贵的全量总结。

## 7. 思考透明度

MindScape 展示的是可观察工作轨迹，而不是声称拿到了模型的全部内部思维：

| 展示层 | 可信含义 |
| --- | --- |
| 系统事件 | 实际选了哪些上下文、挂载哪些能力、调用哪些工具、发生什么状态变化 |
| Provider 思考摘要 | 厂商明确返回的 reasoning summary；没有返回就不伪造 |
| 证据与逻辑验证 | MindScape 根据输入、来源和工具结果重建的可回溯关系 |
| 模型自述 | 模型对自身方法的描述，只能标为自述，不能当作内部过程证据 |

运行详情至少包含：模型、思考模式和预算、有效参数、输入/输出/思考 Token、上下文片段、工具调用、未引用范围、来源和验证警告。原始 `reasoning_content` 是否保存、保存多久和是否展示，应由用户隐私设置与 Provider 条款共同决定；它不能进入普通 assistant 正文或被下一轮无条件带入。

## 8. 用户体验示例

用户在一个已经有 40 轮产品讨论的会话中输入：

> “现在只讨论模型思考等级和上下文成本，给我一个能落地的方案。”

MindScape 不把 40 轮全部发送，而是：

1. 新建一个 FocusFrame，目标是“模型控制与上下文成本”。
2. 保留项目中已确认的产品边界、M1 Go 和 Frozen V1 上下文契约。
3. 检索历史中与思考模式、Token、ContextSnapshot 直接相关的 6 个证据片段。
4. 排除 34 个与视觉、Provider 旧故障和已否决方案有关的片段，并在账单中列明原因。
5. 用户选择“标准思考、当前问题 + 项目记忆、工具先询问、输出 2k”。
6. 模型获得一份约 2,500 Token 的上下文包，而不是不断增长的全量剧本。

用户随后问“那 M1 的 DeepSeek 空正文问题怎么办？”时，可以继续当前 FocusFrame；系统只追加上一轮结果和相关证据，不重新注入 40 轮历史。用户若要恢复原始聊天语境，再选择“原样续接”。

## 9. 分阶段落地

### M1 之后的第一切片：运行控制可见化

- Provider 模型能力目录。
- 有效运行档案和发送前能力校验。
- 模型选择、思考模式、输出预算和上下文策略的 UI。
- ContextSnapshot 展示实际选择与排除项。
- reasoning、正文、工具、用量事件分离。

### 第二切片：聚焦连续性

- FocusFrame 和从节点分支。
- 短期工作记忆、活动分支记忆和项目记忆的版本化结构。
- 建议记忆、用户确认、冲突和失效。
- 相关度 / 决策价值门控与检索预算。

### 第三切片：跨模型比较与验证

- 同一 ContextSnapshot 下切换不同模型运行，旧运行不可改写。
- 记录不同思考预算、成本、延迟和结果差异。
- 对高价值结果运行证据与约束验证。
- 形成“原样续接”和“聚焦续接”的并排比较。

### 暂不进入

- 自动生成任意新 Skill。
- 无限并发的多模型辩论。
- 依赖隐藏思维链的产品承诺。
- 全自动把所有历史压缩成一份不可审计的大摘要。

## 10. 验收标准

1. 同一问题分别使用“当前问题”和“原样续接”时，ContextSnapshot 能证明两者范围不同。
2. 40 轮会话在聚焦模式下不会把全部历史发送给 Provider，且排除范围可见。
3. 用户切换模型只影响下一次运行，既有节点、运行和快照不被修改。
4. 思考模式和预算在 Provider 支持时准确映射；不支持时明确阻止或提示，不静默降级。
5. `reasoning_content` 只有在 Provider 明确返回时才显示为思考摘要，不能替代正文，也不能造成空正文成功。
6. 每轮可查看有效模型、参数、上下文、工具、Token、费用和未解决的不确定项。
7. 用户否决一条建议记忆后，相关推断在后续上下文中不再作为已确认事实使用。
8. 任何外部或不可逆工具调用仍遵循单独的用户确认门禁。

## 11. 待创始人确认的产品选项

- 简洁用户的默认运行档案是否只显示“快速 / 标准 / 深入”，还是增加“自动建议但需确认”。
- 项目记忆是否默认参与聚焦续接，还是每个新 FocusFrame 都要求用户选择。
- 思考摘要的保留时长、展示级别和隐私开关。
- 首批支持哪些 Provider 的 reasoning 控制，以及不支持关闭思考的模型如何呈现。
- “原样续接”是否作为明显入口，避免高级用户误以为系统默认保留全部历史。
