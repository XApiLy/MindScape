## 本轮关闭的 B 编号

### B2：员工02原子持久化与恢复子阻断关闭

- `BEGIN IMMEDIATE` 同一事务内重新读取 lifecycle、冻结候选与源实体，调用 `plan_focus_promotion_decision` 后一次提交 decision、源/目标实体、FTS、Vector 和删除关联关系；memory/lifecycle/entity 任一陈旧均无部分写入。
- `confirm` 只确认 FocusFrame 源实体；`promote` 确认源实体并严格 `INSERT` 新 conversation/project 实体，保留 EvidenceRef；`reject` 删除 FTS/Vector 可检索记录；`delete` 删除实体、关系、FTS/Vector，但不删除 decision tombstone。
- 持久 projection 读取时会与原始不可变请求交叉校验 contract、动作、目标、版本、revision 与时间，损坏或不一致数据不会静默进入 UI。
- Vault 与 SQLite 采用可恢复事务日志：写 Vault 前记录实体、来源页和全局索引 pre-image；SQLite 冲突立即恢复全部文件。若进程在两阶段之间退出，启动时根据 SQLite 是否已有该 `decisionId` 决定保留新投影或恢复旧投影，并清理 journal。
- 同一 ID 重试先读 immutable decision，因此源实体已确认或已删除也能返回原 projection；重试同时会修复缺失的 Vault 投影。

## 跨模块证据

1. `focus_promotion_confirm_is_atomic_idempotent_and_restart_durable`：领域计划 → SQLite v16 → FTS/Vector → 关闭重开数据库，证明同 ID 仅一条记录且重启返回同一 projection。
2. `focus_promotion_promote_creates_a_distinct_confirmed_target_atomically`：FocusFrame 候选 → 源实体确认 → project 实体新建 → FTS/Vector 双记录；不同 ID 决策同一候选被唯一门禁拒绝。
3. `focus_promotion_reject_removes_candidate_from_fts_and_vector` 与 `focus_promotion_delete_keeps_tombstone_and_removes_relations_and_indexes`：否决/删除跨实体、检索、关系和 tombstone 的终态一致。
4. `stale_focus_promotion_rolls_back_decision_and_derived_indexes` 与 `focus_promotion_sqlite_conflict_restores_all_vault_files`：陈旧 revision 或目标 ID 冲突时，SQLite、实体、FTS/Vector、Vault 实体文件和索引均保持原样。
5. `focus_promotion_journal_rolls_back_uncommitted_and_keeps_committed_projection`：模拟崩溃后，未提交 decision 恢复旧 Vault，已提交 decision 保留新 Vault。
6. `focus_promotion_decision_updates_vault_filters_reclose_and_survives_restart`：正式 application service → Vault → candidate filter → Reopen/Close → 服务重启 → decision query；并验证幂等重试修复缺失文件。
