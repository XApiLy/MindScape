## Review Lab 是什么、解决什么问题

Review Lab 位于 `tools/review-lab/`，用于把一次可判断的工程推进保存成不可覆盖的界面版本，让创始人不只通过文字、截图或最终成品判断设计。

它完成以下闭环：

```text
员工完成一个可评审切片
→ 员工明确标记 preview 或 full
→ Review Lab 串行编译 MindScape
→ 保存本次交互预览、代码版本、构建日志和说明
→ 创始人打开当前版、历史版或并排比较
→ 记录确认、修改、否决或后置结论
→ 员工06转成视觉规格，或转交员工03/04及对应领域员工落实
```

历史构建不会被下一次编译覆盖。构建失败也会作为失败版本保留，便于追溯问题和修复结果。

## 哪些推进需要标记

满足下列任一条件时，负责人可以标记一个可评审版本：

- Chat、画布、设置、运行状态、错误、恢复或视口出现创始人可以实际判断的变化。
- 跨团队纵向切片首次贯通，需要确认真实操作是否符合预期。
- 员工准备请求视觉、交互、流程或原生窗口验收。
- M1 Alpha、里程碑或重要风险修复需要保存可复现界面证据。

以下情况不要单独标记：

- 只有代码整理、文档更新或内部测试数字变化，界面和用户流程没有可判断变化。
- 工作仍处于明显不可运行的中间状态，员工尚未准备接受反馈。
- 为了“显示进度”而重复构建没有实质差异的版本。

```powershell

```

负责人界面：`http://127.0.0.1:4178`

## 四种确认方式

### 方式一：GUI

打开 `http://127.0.0.1:4178`，点击“标记可评审版本”，填写：

- 版本名称。
- 提交员工。
- 本次推进内容。
- 请创始人重点确认什么。
- `preview` 或 `full` 构建等级。

适合创始人、员工06或希望通过表单确认内容的员工。

### 方式二：CMD / PowerShell 交互确认

在 `tools/review-lab/` 中运行：

```powershell
npm run mark
```

命令会逐项询问版本名称、提交员工、推进内容、重点确认项和是否需要完整 Windows 构建。适合员工完成切片后手动确认。

### 方式三：员工 Agent 或脚本非交互确认

员工代理可使用参数一次性提交：

```powershell
npm run mark -- --title "停止状态视觉" --author "员工04" --summary "完成停止中、取消失败回退和cancelled三态" --focus "请确认停止按钮反馈与部分内容保留" --preview
```

参数要求：

- `--title`、`--author`、`--summary` 必填。
- `--focus` 建议填写，必须是创始人能够判断的问题。
- 普通界面评审使用 `--preview`；关键原生验收使用 `--full`。
- 标题和说明禁止包含API Key、用户正文、完整请求响应或其他秘密。

### 方式四：Git提交标记自动识别

Review Lab每10秒检查一次新的 `HEAD`。只有提交正文含明确Trailer时才会自动进入构建队列：

```text
Review-Lab: preview
Review-Title: Chat 停止交互第一版
Review-Author: 员工04
Review-Summary: 完成停止中、取消失败回退和cancelled呈现
Review-Focus: 请确认停止按钮位置和三态视觉层级
```

规则：

- `Review-Lab` 只允许 `preview` 或 `full`。
- 同一提交只消费一次。
- 服务启动时不补编译过去没有消费的旧提交。
- 普通提交、普通PEC替换和工作区文件变化不会触发。
- 可运行 `npm run scan` 要求立即扫描当前HEAD，但没有新显式信号时仍不会构建。

## HTTP连接

其他本机员工工具、Agent或后续CI可以调用：

```text
POST http://127.0.0.1:4178/api/versions
Content-Type: application/json
```

请求示例：

```json
{
  "title": "画布视口恢复",
  "author": "员工03",
  "summary": "完成多会话视口持久化",
  "focus": "请确认切换会话与重启后的视口是否稳定",
  "buildMode": "preview"
}
```

当前接口没有团队身份认证，只允许 `127.0.0.1` 本机连接。未增加认证前不得开放到局域网或公网。

## preview 与 full 如何选择

### `preview`｜默认

- 编译并保存 MindScape 前端生产版本。
- 可直接嵌入 Review Lab 操作和并排比较。
- 适合视觉、布局、Chat、画布和大部分交互状态评审。
- 使用现有 Mock Preview，不替代真实Provider、凭据和崩溃恢复验收。

### `full`｜关键版本

- 先保存交互预览，再编译并归档完整 Windows Tauri 构建。
- 从 Review Lab 点击“启动完整版本”后，以独立窗口运行历史副本。
- 只用于真实Provider、系统凭据、SQLite、原生窗口、恢复、Alpha和里程碑验收。
- 耗时和磁盘占用更高，不能每个小推进都使用。

## 构建后员工要做什么

- `ready`：可以请求创始人评审。
- `warning`：构建期间源码发生变化；预览可查看，但不能宣称严格可复现，应停止修改后重新标记。
- `failed`：查看“构建记录”，修复后建立新的版本，不覆盖或删除失败历史。
- 员工在请求评审时必须指出版本名称和“重点确认项”，不能只说“请看看”。
- 创始人的确认、修改、否决和后置结论绑定到具体版本；员工06负责将体验结论整理为规格或转派任务。
- 员工03、04继续负责画布与Chat工程正确性；员工01、02、05继续负责各自领域、数据和Provider事实，Review Lab不改变所有权。
