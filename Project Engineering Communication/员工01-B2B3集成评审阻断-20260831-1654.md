## 评审发现

### B2/B3-REV-01：Delete 后存活实体 Vault 页保留悬空 Wikilink

- `MarkdownVault::apply_focus_promotion_plan` 在 `DeleteSource` 分支把 `projected` 设为空，只备份并删除候选实体文件、重写实体索引；它没有把删除前 relation 的邻接实体文件纳入同一 journal，也没有用删除后的 relation 集合重投影这些存活实体。
- SQLite transaction 会删除所有关联 relation、FTS 和 Vector；因此正常返回后可能出现“SQLite relation 已为 0、被删实体文件已消失，但另一实体 `.md` 仍含 `[[deleted-id]]`”的双权威分裂。`project_persisted_focus_promotion` 的 Delete 重放路径同样只删候选文件和重写索引。
- 现有 B5 审计只核对候选 relation 行数和候选 Vault 文件存在性，不扫描存活实体页的 managed Wikilink，故无法捕获该问题。

要求员工02修复：将删除前所有邻接实体文件及相关来源页纳入同一个 Vault journal，按删除后的 relation 集合重投影；同时覆盖首次执行、SQLite 冲突回滚、已提交 decision 重放和进程重启。新增跨模块测试必须直接断言：SQLite relation=0、被删文件不存在、存活实体页不含被删 ID、重启和同 ID 重放后仍一致。

### B3-REV-02：DiscussionLog 失败补偿未覆盖 EvidenceRef 与讨论索引

- `write_discussion_log` 在 SQLite 落库前逐个写入 `sources/<evidence-id>.md`，随后才写讨论日志文件。
- `project_discussion_log_markdown` 遇到 SQLite 外键/修订失败时只恢复上一日志或删除首次日志，没有恢复/删除本次新建或覆盖的来源页。若来源 ID 复用，还会把原来源页永久覆盖。
- 讨论索引在 SQLite 成功提交后才单独写入；该步失败会返回错误，但 SQLite 已提交，启动流程也没有按 SQLite 权威状态重建 `indexes/discussions.md`，故错误返回和重启后仍可能保留旧索引。

要求员工02修复：为 DiscussionLog 的日志文件、所有 EvidenceRef 来源页和讨论索引建立同一可恢复 journal；SQLite 失败需字节级还原旧文件并删除新孤儿，SQLite 已提交但索引写入/进程中断时启动需按已提交 revision 收敛。新增测试至少覆盖：新 EvidenceRef + 外键失败无孤儿、复用 EvidenceRef + 外键失败旧文件字节不变、索引写入故障、提交前/后重启恢复。
